# F10.2 / F11.8 — scout-only repro (non-`.eval`)

These two findings share a single root cause and a single code path that is
**unreachable from `apps/inspect`**. They were removed from the `.eval` repro
set (see [`REMOVED.md`](../../REMOVED.md)) because `inspect view` renders the
test data correctly. This document is the replacement repro: a source-level
walk-through, manual verification steps for someone with scout running, and a
drop-in vitest unit test that demonstrates both bugs against the component
directly.

| Finding | Claim | Original verdict |
|---|---|---|
| **F10.2** | Standalone tool message never shows `message.error` | [verify/per-finding/F10.2.md](../../verify/per-finding/F10.2.md) — REPRO_BROKEN (scout-only) |
| **F11.8** | Standalone tool message drops non-text/image content (`ContentData`, `ContentDocument`, …) | [verify/per-finding/F11.8.md](../../verify/per-finding/F11.8.md) — REPRO_BROKEN (scout-only) |

---

## (a) The exact source bug

`src/inspect_ai/_view/ts-mono/packages/inspect-components/src/chat/ChatMessage.tsx:116-129`

```tsx
{isNonTaskTool ? (
  <ToolOutput
    output={
      typeof message.content === "string"
        ? message.content
        : message.content.filter(
            (c): c is ContentText | ContentImage =>
              c.type === "text" || c.type === "image"
          )
    }
  />
) : (
  <MessageContents key={`${id}-contents`} message={message} />
)}
```

where `isNonTaskTool = message.role === "tool" && message.function !== "Task"`
(line 43).

Two defects, both on the `isNonTaskTool` branch:

1. **F10.2** — `message.error` (`ToolCallError | null`, schema
   `generated.ts:607`) is never read. A failed tool call rendered through this
   branch shows only its `content` array — typically empty on error — so the
   failure is invisible. Contrast `ChatMessageRow.tsx:228-231`
   (`resolveToolMessage`), which substitutes `error.message` for content on the
   collapsed path.
2. **F11.8** — the `.filter()` keeps only `text | image`. `ToolOutput.tsx:34-65`
   already handles `document`, `reasoning`, and `data`, so the pre-filter is
   strictly lossy. A `ContentData` block that the collapsed path renders as a
   key-value tree is silently dropped here.

---

## (b) Why this is scout-only

The `isNonTaskTool` branch fires only when a `role: "tool"` message reaches
`ChatMessage` directly — i.e. when it was **not** folded into the preceding
assistant row. That requires `tools.collapseToolMessages === false`:

- `ChatView.tsx:38` — `const resolveInto = tools?.collapseToolMessages ?? true;`
- `ChatViewVirtualList.tsx:131` — same default.

Grep for who sets it `false` (full monorepo):

| Caller | File:line | Reachable from |
|---|---|---|
| ref-preview popover (single message) | `apps/scout/src/app/utils/refs.tsx:132` | scout scan-result page |
| ref-preview popover (messages array) | `apps/scout/src/app/utils/refs.tsx:146` | scout scan-result page |
| ref-preview popover (transcript input) | `apps/scout/src/app/utils/refs.tsx:208` | scout scan-result page |
| `ModelEventView` input/output panes | `packages/inspect-components/src/transcript/ModelEventView.tsx:142,192` | only when `context?.hasToolEvents === false`; in `apps/inspect` the transcript always has tool events when tool messages exist, so this stays `true` |

`apps/inspect` never sets it `false`; its Messages tab (`SampleDisplay.tsx`)
passes `tools={{ callStyle: "complete" }}` and takes the default.
**Even scout's own Messages tab** (`apps/scout/src/app/transcript/TranscriptBody.tsx:306-321`)
takes the default — the only scout surface that hits this branch is the
**citation-reference preview popover** rendered by
`MarkdownDivWithReferences` → `citePreview()` on a scan-result detail page.

Scout is served by an `inspect_scout` FastAPI backend
(`vite.config.ts:97-101` proxies `/api → http://127.0.0.1:7576`); it does not
read `.eval` files. The scout e2e suite mocks that backend with MSW
(`apps/scout/e2e/fixtures/`), but the existing handlers cover only
`/api/v2/transcripts/*`, not the `/api/v2/scans/*/results/*` + scanner-input
endpoints needed to reach a citation popover. Building that mock surface +
`pnpm install` + Playwright browser install exceeded the 15-min timebox, so
this repro falls back to a unit test.

## (c) Manual verification (for someone with scout running)

Prerequisite: a working `inspect_scout` checkout with the FastAPI backend on
`:7576` and `pnpm dev` on `:5173`, plus at least one completed scan whose
scanner returned a `ScanResultSummary` with `messageReferences`.

1. In the scan's source data, ensure one referenced message is a
   `ChatMessageTool` shaped like:

   ```jsonc
   {
     "id": "tool-msg-1",
     "role": "tool",
     "function": "rich_tool",
     "tool_call_id": "call-1",
     "content": [
       { "type": "text", "text": "text part survives ✓" },
       { "type": "data",
         "data": { "sentinel": "F11.8_CONTENTDATA_SENTINEL_if_missing_bug_confirmed",
                   "n": 42 } }
     ],
     "error": { "type": "timeout",
                "message": "F10.2_ERROR_FIELD_timeout — exceeded 30s" }
   }
   ```

   and that the scanner emitted a citation `[^…]` pointing at `tool-msg-1`.

2. Open the scan-result detail page
   (`#/scans/<dir>/<scanPath>/<resultIdentifier>`). In the result body
   markdown, hover or click the citation chip for `tool-msg-1` so the
   `citePreview` popover opens.

3. **Bug observation:**
   - Popover header reads `tool: rich_tool`.
   - Body shows **only** `text part survives ✓` inside a `<pre.tool-output>`.
   - The `F11.8_CONTENTDATA_SENTINEL_…` key-value block is **absent** (F11.8).
   - The `F10.2_ERROR_FIELD_timeout …` string is **absent** (F10.2).

4. **Cross-check (correct behaviour, same data):** open scout's Messages tab
   for the same transcript. The tool result there is collapsed under the
   assistant row via `ToolCallView` and shows the error string *and* the
   `ContentData` tree — proving the data is intact and only the standalone
   path drops it.

## (d) Vitest unit test

The buggy component lives in `@tsmono/inspect-components`, which already has
`@testing-library/react` + `jsdom` as devDependencies and a `test` script.
Drop the file below at
`packages/inspect-components/src/chat/ChatMessage.scoutOnly.test.tsx` and run
`pnpm --filter @tsmono/inspect-components test` from `ts-mono/`.

> Both tests are written to **fail on current `main`** (demonstrating the
> bug) and pass once F10.2/F11.8 are fixed. To use them as a regression check
> *of the bug's presence* instead, invert the final `expect`s.

```tsx
// @vitest-environment jsdom
import { cleanup, render } from "@testing-library/react";
import { afterEach, describe, expect, it } from "vitest";

import type { ChatMessageTool } from "@tsmono/inspect-common/types";

import { ChatView } from "./ChatView";

afterEach(cleanup);

// A tool message carrying (a) a ContentData block that ToolOutput knows how to
// render, and (b) a ToolCallError. Rendered with collapseToolMessages:false
// this exercises ChatMessage.tsx:116-129 — the scout citation-preview path.
const toolMsg: ChatMessageTool = {
  id: "tool-msg-1",
  role: "tool",
  function: "rich_tool",
  tool_call_id: "call-1",
  source: "generate",
  content: [
    { type: "text", text: "text part survives" },
    {
      type: "data",
      data: { sentinel: "F11_8_CONTENTDATA_SENTINEL", n: 42 },
    },
  ],
  error: {
    type: "timeout",
    message: "F10_2_ERROR_FIELD_timeout exceeded 30s",
  },
};

describe("ChatMessage standalone tool path (collapseToolMessages: false)", () => {
  it("F11.8 — passes ContentData through to ToolOutput (currently FAILS)", () => {
    const { container } = render(
      <ChatView
        id="repro"
        messages={[toolMsg]}
        tools={{ collapseToolMessages: false }}
      />,
    );
    // Sanity: we are on the standalone branch, not ToolCallView.
    expect(container.querySelector("[class*='toolCallView']")).toBeNull();
    expect(container.textContent).toContain("text part survives");

    // BUG: ContentData is filtered out before ToolOutput sees it.
    // ToolOutput.tsx:60-63 would otherwise render JSON.stringify(out.data),
    // which contains the sentinel.
    expect(container.textContent).toContain("F11_8_CONTENTDATA_SENTINEL");
  });

  it("F10.2 — renders message.error on the standalone path (currently FAILS)", () => {
    const { container } = render(
      <ChatView
        id="repro"
        messages={[toolMsg]}
        tools={{ collapseToolMessages: false }}
      />,
    );
    // BUG: ChatMessage never reads `message.error` on the isNonTaskTool branch.
    // The collapsed path (resolveToolMessage, ChatMessageRow.tsx:228-231) does.
    expect(container.textContent).toContain(
      "F10_2_ERROR_FIELD_timeout exceeded 30s",
    );
  });

  it("control — collapsed path DOES show the error (passes today)", () => {
    // Pair the tool message with an assistant tool_call so resolveMessages()
    // folds it into the assistant row → ChatMessageRow → ToolCallView.
    const { container } = render(
      <ChatView
        id="control"
        messages={[
          {
            id: "asst-1",
            role: "assistant",
            content: "calling tool",
            source: "generate",
            tool_calls: [
              {
                id: "call-1",
                type: "function",
                function: "rich_tool",
                arguments: {},
              },
            ],
          },
          toolMsg,
        ]}
        tools={{ collapseToolMessages: true }}
      />,
    );
    expect(container.textContent).toContain(
      "F10_2_ERROR_FIELD_timeout exceeded 30s",
    );
  });
});
```

### Why no Playwright script

A Playwright repro against scout would need to:

1. `corepack enable && pnpm install` (~2 min, not currently installed in this
   tree) + `npx playwright install chromium`.
2. Extend `apps/scout/e2e/fixtures/handlers.ts` with MSW mocks for
   `GET /api/v2/scans/:dir/:scanPath`,
   `GET /api/v2/scans/:dir/:scanPath/results/:identifier`, and the
   scanner-input endpoint that feeds `referenceTable()` — none of which exist
   yet.
3. Drive `MarkdownDivWithReferences` to open the `citePreview` popover.

Step 2 alone is a non-trivial fixture-authoring task against
`scout/openapi.json`; the unit test above hits the identical code path
(`ChatView` with `collapseToolMessages: false` → `ChatMessage` →
`isNonTaskTool` → `ToolOutput`) for a fraction of the cost and with no
backend.

## Suggested fix (for reference, not applied)

```tsx
// ChatMessage.tsx — isNonTaskTool branch
{isNonTaskTool ? (
  message.error ? (
    <ToolOutput output={message.error.message} />
  ) : (
    <ToolOutput
      output={
        typeof message.content === "string"
          ? message.content
          : message.content.filter(
              (c): c is Exclude<Content, { type: "tool_use" }> =>
                c.type !== "tool_use",
            )
      }
    />
  )
) : (
  <MessageContents key={`${id}-contents`} message={message} />
)}
```

This mirrors `resolveToolMessage` for the error case and matches
`ToolOutputProps.output`'s declared element type (`Exclude<Content,
{type:"tool_use"}>`), fixing both findings in one diff.
