# F10.4 — Citation `<sup>` numbers don't match the footnote list

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 10-chat | **Port:** 7624 | **Log:** `2026-04-24T03-26-12-00-00_F10.4-citation-numbering-mismatch_nNrxCMoT78wRMJgUEM54VK.eval`

## What the finding claims

`MessageContent.tsx:320-371` numbers positional-cite `<sup>` markers per text-block via `positionalCites.length - i` (no `citeCount` offset), while `MessageCitations.tsx:23-28` numbers the footnote list as `index + 1` over the *flattened* citation array. With ≥2 coalesced text blocks the two schemes diverge.

## What the repro's bug_description says to look for

> **Observed:** Inline superscripts in BLOCK 2 restart from 1 (so both blocks show ¹ ²), while the footnote list runs 1–4. Clicking footnote #3 (CITE-C) maps to no inline ³.
> **Expected:** Inline superscripts run 1, 2, 3, 4 across both blocks and line up 1-for-1 with footnotes CITE-A … CITE-D.

## What I actually observed

## Analysis

- **Mismatch is real:** inline `[1,2,1,2]` vs footnotes `[1,2,3,4]`. Footnotes 3 and 4 have no corresponding inline marker; inline `¹` after "Germany" points the reader at footnote 1 (CITE-A, about Paris) when the actual source is CITE-C.
- **Is it actually confusing? Yes.** The `<sup>` elements are bare `<sup>N</sup>` inside a `<p>` — no `<a>` wrapper, no `href`, no `id`/anchor. There is **no click-through or hover linkage** between an inline marker and its footnote; the number is the *only* correlation mechanism. So a wrong number = wrong attribution, full stop.
- **Source confirms root cause:** `MessageContent.tsx:341-349` computes the sup label as `positionalCites.length - i` with `citeCount` updated *after* the loop, so each `ContentText` in the coalesced run restarts positional numbering at 1. `MessageCitations.tsx:23-28` numbers the `flatMap`'d list `index + 1`. Exactly as the finding states.
- Prior verdict (CONFIRMED) was correct; the earlier "repro fixed — `cited_text` → tuples" note is accurate (string `cited_text` would have taken the end-cite branch which *does* share `citeCount` and would not repro).

## Recommended action

Keep as-is (MEDIUM). Fix should change line 346 to `<sup>${citeCount + (positionalCites.length - i)}</sup>` (or build a single ordered citation array and number from it for both inline and list, which also fixes the secondary ordering issue when positional cites are not in source order).
