## What the finding claims

`ModelEventView.tsx:46-48` extracts only `choice.message` from `output.choices`, dropping `stop_reason`; line 150 renders `event.error` but never `event.output.error`. Result: a `max_tokens`-truncated or content-filtered completion is indistinguishable from a normal one in the event UI.

## What the repro's bug_description says to look for

> **Observed:** The assistant message just… ends. No `max_tokens` badge, no indication the completion was truncated. No sign of the `output.error` refusal text (`⚠️ PROVIDER REFUSAL …`).
> **Expected:** `stop_reason` shown when ≠ `stop`/`tool_calls`; `output.error` rendered in the Error section.

## Analysis

**Verdict CONFIRMED** — agrees with prior verdict.

- **Source code matches the claim.** `ModelEventView.tsx:46-48`: `event.output.choices?.map((choice) => choice.message)` — `stop_reason` is dropped. Line 150-153: `{event.error ? <EventSection title="Error">…` — reads `event.error`, never `event.output.error`. A repo-wide grep confirms `stop_reason` is not consumed by any rendering component (only test fixtures and `timeline/syntheticNodes.ts` which hard-codes `"stop"`).
- **Is `stop_reason` shown elsewhere?** No. Checked the sample **Messages** tab (ChatView) — assistant messages render content only, no stop-reason chip. The grep hits for "max_tokens"/"stop_reason" in the Messages/Summary/All tabs are entirely bleed-through from the embedded bug-description user message; once that is excluded, neither term appears as viewer chrome.
- **Is `output.error` shown elsewhere?** Partially: `transcript/timeline/markers.ts:56,79` reads `event.output.error` to paint a red error **marker on the timeline strip** and uses the string as the marker tooltip. That surfaces *that* an error occurred but not in the event panel where users actually read the conversation, and it doesn't help with `stop_reason` at all. The finding's claim "never surfaced **in ModelEvent**" remains accurate.
- **User impact is real**: a truncated (`max_tokens`/`model_length`) or content-filtered completion looks identical to a normal `stop` completion in the transcript — exactly the debugging gap the finding describes.

The prior check (`checks/F04_7.py`) used the same `'content filtered'` sentinel and label-set approach and was correct; this re-verification adds screenshots, the Messages-tab cross-check, and the timeline-marker caveat.

## Recommended action

Keep as-is (MEDIUM). Fix per the finding's suggestion: render a per-choice `stop_reason` chip when ∉ {`stop`, `tool_calls`}, and fall back to `event.output.error` in the Error section when `event.error` is null.
