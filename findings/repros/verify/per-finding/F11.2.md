# F11.2 — `ToolCallError.type` is never displayed

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 11-tools | **Port:** 7628 | **Log:** `2026-04-23T04-58-08-00-00_F11.2-tool-error-type-dropped_TYWa7DvqCLr7KRdVFSJrDp.eval`

## What the finding claims

`ToolCallError` carries a typed enum (`"parsing" | "timeout" | "permission" | …`) but only `.message` is ever read by the viewer; `.type` is dropped in every render path. Cited: `transcript/ToolEventView.tsx:110` (`event.error?.message || event.result`) and `chat/ChatMessageRow.tsx:230` (`toolMessage.error.message`).

## What the repro's bug_description says to look for

> **Observed:** Only the `.message` text is rendered. The enum value `type='permission'` does not appear anywhere in the UI. Ctrl-F for `F11.2_TYPE_FIELD_VALUE_permission` → 0 matches.
> **Expected:** Error rendered as e.g. `permission: <message>` so the diagnostic category is visible.

## Analysis

The verdict matches the prior check; the source-code reading is correct on both cited lines (verified at current HEAD), and a repo-wide grep finds **zero** reads of `error.type` in any viewer render path (the only hit is in `timeline/markers.test.ts`). The rendered tool result is exactly `error.message` and nothing else.

Adversarial notes:

- **Repro sentinel is a red herring.** The repro's "Ctrl-F for `F11.2_TYPE_FIELD_VALUE_permission`" instruction is meaningless — that string was never assigned to `error.type` (the type is the literal `"permission"`); the sentinel only appears in the bug-description and `.message` prose. The valid evidence is the gap-analysis / DOM-scrub above, not the sentinel grep.
- **Transcript path not exercised.** The repro injects `ChatMessageTool` directly without invoking a tool, so no `ToolEvent` is emitted and the Transcript tab shows zero event panels. `ToolEventView.tsx:110` is therefore source-confirmed only, not screenshot-confirmed. (This does not change the verdict — `ChatMessageRow.tsx:230` is fully demonstrated.)
- **Not BY_DESIGN.** No comment near either line suggests intentional suppression; and `_call_tools.py:208-212` constructs `parsing` / `approval` / `unknown` errors whose `.message` does *not* self-identify the category, so the type carries real signal that is currently lost.

Impact is real but bounded: most built-in error messages (`timeout`, `file_not_found`, `limit`) self-describe in `.message`; the loss is sharpest for `parsing` / `approval` / `unknown` and for user-authored `ToolCallError`s. MEDIUM severity is appropriate.

## Recommended action

Keep as-is (CONFIRMED, MEDIUM). Suggested fix per the finding: render `` `${error.type}: ${error.message}` `` (or a small badge) in both `ToolEventView.tsx:110` and `ChatMessageRow.tsx:230`. Optionally tidy the repro: drop the misleading sentinel-grep instruction, or use a real tool call so a `ToolEvent` lands in the Transcript.
