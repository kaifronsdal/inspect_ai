## Analysis

The **observed behaviour is exactly as the finding describes** — silent deletion, no marker. However, this is **deliberate, documented, and tested**:

1. **Design doc** — `src/inspect_ai/_view/ts-mono/design/migration/chat-migration.md:48`:
   > | **Internal tag stripping** | Removes `<internal>`, `<content-internal>` tags | Removes `<internal>`, `<content-internal>`, `<think>` tags | **Merged: strips all three tag types** |

   And the manual test plan at line 160–161:
   > **Think tag stripping** — Verify `<think>`, `<internal>`, `<content-internal>` tags are removed from assistant text.

2. **e2e test** — `apps/scout/e2e/chat-components.spec.ts:623-654` (`"strips internal tags from text content"`) explicitly asserts the stripped body is **not** visible and asserts nothing about a marker.

3. **Commit intent** — `d6fb9a219` (PR #2324) added it with sub-commits "Remove internal contains of content" / "correct internal content purging".

4. **Architectural rationale** — these three tags are inspect's **bridge serialisation envelopes**, not user content:
   - `<content-internal>` / `<internal>` carry **base64-encoded JSON** smuggled through plain-text channels (`model/_internal.py:7-47`). Rendering them would show garbage; a "[hidden]" marker would be pure noise on every bridged message.
   - `<think>` is the wire format produced by `reasoning_to_think_tag()` (`model/_reasoning.py:98-121`) when `ContentReasoning` is flattened to text for the agent bridge. In normal flows the model layer calls `parse_content_with_reasoning()` to lift it back into a `ContentReasoning` block — which the viewer **does** render with a "Reasoning" header and collapse toggle (`MessageContent.tsx:174-219`). The text-renderer strip is defensive cleanup for the leak case where a bridge round-trip left the wrapper in plain text (cf. `model/_openai.py:564` "sub-agent tool call that has `<think>` or `<internal>` smuggled inside").

The finding's scenario — "open-weights models via raw completion emit `<think>…</think>`" — is real (DeepSeek-R1, QwQ), but inspect's providers extract those into `ContentReasoning` before the log is written, so they hit the `reasoning` renderer, not this strip path. The repro reaches this path only by hand-constructing a `ChatMessageAssistant` with a raw string and bypassing `generate()`.

**Why the prior CONFIRMED verdict was wrong:** the previous check (`checks/F10_6.py`) verified only that the body is gone with no marker — true — but did not investigate whether that is intentional. The protocol's BY_DESIGN criterion ("comments, git blame, or obvious design rationale") is squarely met here by a design doc, an e2e test, and the bridge-smuggling architecture.

A "[hidden reasoning]" placeholder or a fallback that promotes leaked `<think>` text into the `reasoning` renderer would be a reasonable **enhancement**, but the current silent strip is the designed behaviour, not a regression or oversight.

## Recommended action

**Remove finding** (or reclassify as a low-priority enhancement request: "promote leaked `<think>` text to the Reasoning renderer instead of dropping it"). Do not track as a MEDIUM bug.
