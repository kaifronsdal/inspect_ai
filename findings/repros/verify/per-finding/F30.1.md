# F30.1 — Per-metric score columns collide when multiple scorers share a metric name

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 30-loglist | **Port:** 7642 | **Log:** `2026-04-24T01-25-01-00-00_F30.1-metric-collision-{a,b}_*.eval`

## What the finding claims

`apps/inspect/src/app/log-list/grid/columns/hooks.tsx:43-63` and `LogListGrid.tsx:204-215` key dynamic score columns by bare `metricName` (`row[\`score_${metricName}\`]`, `scoreTypes[metricName]`). When ≥2 scorers each report `accuracy`, the inner loop overwrites the slot — last scorer in `results.scores` wins, header gives no scorer attribution.

## What the repro's bug_description says to look for

> **observed:** Only ONE `accuracy` column appears (and one `stderr`). Its value is whichever of `scorer_alpha` (0.0) or `scorer_beta` (1.0) was iterated last … `row[\`score_${metricName}\`]` is overwritten per scorer.
> **expected:** Two accuracy columns: `scorer_alpha/accuracy = 0.0` and `scorer_beta/accuracy = 1.0`.

## What I actually observed

**Screenshot:** `artifacts/per-finding/F30.1-page.png` (column selector open), `artifacts/per-finding/F30.1-grid.png` (accuracy column enabled)

The "Choose Columns" popover shows a **Scorers** section with exactly two checkboxes: `accuracy` and `stderr` — one entry per metric name, not per scorer. After enabling `accuracy`, a single right-most column headed "accuracy" appears. Both F30.1 rows show `1.0` in it, while the headline `Score` column for the same rows shows `0.0`.

**DOM evidence:**
```
Column-selector labels (Scorers section): ['accuracy', 'stderr']      ← 1 accuracy checkbox
Grid header col-ids containing 'accuracy':
  [{'colId': 'score_accuracy', 'text': 'accuracy'}]                   ← 1 accuracy column

F30.1_metric_collision_a row:  score=0.0   score_accuracy=1.0
F30.1_metric_collision_b row:  score=0.0   score_accuracy=1.0
```

## Analysis

**Source confirms:** `hooks.tsx:55` writes `scoreTypes[metricName] = …` and `LogListGrid.tsx:211` writes `row[\`score_${metricName}\`] = metric.value` inside a `for (const evalScore of details.results.scores)` loop — bare metric name, no scorer prefix. Code matches the finding exactly.

**Page confirms:** Each F30.1 log has two scorers (`scorer_alpha` → accuracy 0.0, `scorer_beta` → accuracy 1.0). The grid renders **one** `accuracy` checkbox and **one** `score_accuracy` column. The cell shows `1.0` = `scorer_beta` (last element of `scores[]`), so `scorer_alpha`'s `0.0` was overwritten. The header text is just "accuracy" with no scorer hint.

**Smoking gun — internal contradiction in the same row:** the headline `Score` column (computed elsewhere from `scores[0].metrics[first]` = scorer_alpha) shows `0.0`, while the `accuracy` column shows `1.0`. A user looking at one row sees two different "accuracy" numbers for the same eval with no explanation.

**Answering the task's specific questions:**
- *How many `accuracy` columns/checkboxes?* **One** checkbox, **one** column (`score_accuracy`).
- *Do the two F30.1 logs show different accuracy values?* **No** — both rows show `accuracy=1.0` because the repro defines tasks `a` and `b` with the **same** scorer order `[alpha, beta]`. The two logs are redundant; the collision is proven *within* each row by `Score=0.0` vs `accuracy=1.0`, not by row-to-row difference. (If the repro wanted row-to-row proof it should have swapped scorer order in task `b`.)

The prior CONFIRMED verdict stands. Prior VERIFICATION.md note "row shows `1.0` AND `0.0`" refers to the within-row Score-vs-accuracy contradiction, which is accurate.

## Recommended action

Keep as-is (HIGH, CONFIRMED). Optional repro improvement: swap scorer order in `f30_1_metric_collision_b` so the two grid rows show `accuracy=1.0` vs `accuracy=0.0`, making the "which scorer?" ambiguity visually obvious without needing the headline-Score comparison.
