# F04.5 — ModelEvent `retries` and `cache` never displayed

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 01-events | **Port:** 7612 | **Log:** `2026-04-24T01-27-38-00-00_F04.5-model-retries-cache-hidden_ge4oyXte7oehnEvCapbpvE.eval`

## What the finding claims

`ModelEvent.retries` and `ModelEvent.cache` are present in the schema but read nowhere in `src/inspect_ai/_view/ts-mono/packages/inspect-components/src/transcript/ModelEventView.tsx`, so users cannot see that a model call was retried N times or that its output came from the inspect-level response cache.

## What the repro's bug_description says to look for

> **Where:** Transcript tab → expand **Model Call: mockllm/model** → check the title, **Summary**, **All**, and **Timing** tabs
> **Observed:** Nothing anywhere indicates `retries: 3` or `cache: "read"`. The event title, body, and Timing panel are all silent.
> **Expected:** A badge or row showing **3 retries** and **cached (read)**.

## Analysis

Verdict matches the prior batch check, and is supported on three independent axes:

1. **Source:** `ModelEventView.tsx` reads `event.{model, role, input, output, config, tools, tool_choice, call, error, pending, timestamp, completed, working_start, working_time}` and nothing else. `rg "\.retries|\.cache\b"` across the entire `transcript/` component tree returns zero hits; the only `retries` references in the viewer codebase are `sample.retries` (sample-level retry count, an unrelated concept) and an internal work-queue.
2. **Raw data:** The JSON tab proves the log carries `"retries": 3` and `"cache": "read"` on the event, so the synthetic-event injection (`transcript()._event()`) worked and the data reaches the client.
3. **Rendered UI:** Neither the title, the Summary tab, nor the All tab (USAGE / TIMING / MESSAGES sections) surface a retries or cache indicator. The All-tab label set contains no `RETRIES` / `RETRY` / `CACHE` / `CACHED` entry.

This is user-impacting, not cosmetic: a user debugging a slow/flaky model call has no way to learn from the viewer that the request was retried 3× or that the output was served from cache (which materially changes how `output.time` and token usage should be interpreted). MEDIUM severity is appropriate.

The repro's `bug_description` mentions a "Timing tab" — there is no separate Timing *sub-tab*; Timing is a section inside the **All** sub-tab. Minor wording issue only; the location instructions still lead to the right place.

## Recommended action

Keep as-is (CONFIRMED, MEDIUM). Suggested fix per the finding: render a small `cached` / `N retries` badge in the event title and/or add rows under the **All** tab's USAGE/TIMING block.
