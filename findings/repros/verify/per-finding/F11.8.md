# F11.8 — Orphan tool-message content filtered to text+image only

**Prior verdict:** NOT_REPRODUCED (scout-only path, same as F10.2)
**New verdict:** REPRO_BROKEN (source supports finding; unreachable in inspect app)
**Batch:** 11-tools | **Port:** 7632 | **Log:** `2026-04-23T04-58-15-00-00_F11.8-orphan-tool-content-filtered_GKjfh9MjoKSQoHkMd8scfX.eval`

## What the finding claims

`ChatMessage.tsx:117-125` — when a tool message renders **standalone** (not paired under an assistant call), its content array is pre-filtered to `text | image` before being passed to `ToolOutput`, so `ContentData` / `ContentDocument` blocks are silently dropped. The paired-with-assistant path (`ChatMessageRow → ToolCallView → MessageContent`) handles them correctly.

## What the repro's bug_description says to look for

> **Observed:** Only the 'text part survives ✓' line renders. The `ContentData` block carrying `F11.8_CONTENTDATA_SENTINEL_if_missing_bug_confirmed` is gone.
> **Expected:** `ToolOutput` already knows how to render `ContentData` — the pre-filter in `ChatMessage.tsx` should not strip it.
> **Where:** Messages tab **with `collapseToolMessages` OFF**.

## Analysis

**Prior verdict upheld.** The ContentData sentinel is rendered, contrary to the repro's "Observed" claim.

The wrapping element has class `_toolCallView_…` — i.e. it rendered via **`ToolCallView`**, not the cited `ChatMessage → ToolOutput` branch. That confirms the path taken:

- `ChatViewVirtualList.tsx:131` / `ChatView.tsx:38` default `collapseToolMessages` to `true`; only `apps/scout/src/app/utils/refs.tsx:132,146,208` set it `false`.
- With collapse on, the tool message resolves into the preceding assistant row via `ChatMessageRow.tsx:126 resolveToolMessage()`, which at line 263 filters out **only** `tool_use` and passes everything else (incl. `ContentData`) through to `ToolCallView → MessageContent` → `RecordTree` JSON renderer.
- The cited buggy filter at `ChatMessage.tsx:121-124` (`c.type === "text" || c.type === "image"`) sits behind `isNonTaskTool` and is only reached when a tool message arrives at `ChatMessage` directly — i.e. `collapseToolMessages: false`. The inspect viewer never sets that.

The repro itself acknowledges this: its `where_to_look` says "Messages tab with `collapseToolMessages` OFF", a state the inspect viewer has no UI to enter. The repro pairs the tool message with an assistant `tool_call`, guaranteeing the collapsed path; an *orphan* tool message wouldn't help either because F10.1 swallows orphans before render.

**Source code supports the finding.** The filter at `ChatMessage.tsx:121-124` is real and would drop `ContentData`/`ContentDocument`/`ContentReasoning` if reached. It is reachable in `apps/scout`. It is not reachable from `inspect view`.

## Recommended action

Keep finding but **re-scope to `apps/scout`** and downgrade to LOW (inspect-viewer users never see it). The source fix in F11.8 ("filter only `tool_use` out") is still correct and trivial. Mark the repro as scout-only / not verifiable via `inspect view`.
