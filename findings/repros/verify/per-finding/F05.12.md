# F05.12 — BranchEventView discards `event.metadata`

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED_MINOR
**Batch:** 01-events | **Port:** 7621 | **Log:** `2026-04-24T01-27-46-00-00_F05.12-branch-event-omits-metadata_8ANaNYXgcGdbhKZ6Duwafb.eval`

## What the finding claims

`BranchEventView.tsx:23-29` builds its data grid from `from_span` / `from_message` only and never merges `event.metadata`, unlike `CompactionEventView.tsx:30` which does `{ ...data, ...event.metadata }`. Cited schema: `generated.ts:489-491`.

## What the repro's bug_description says to look for

> **Observed:** Only `from_span` and `from_message` are shown. The `metadata` dict (`branch_reason`, `branch_index`, `MARKER`) is **not rendered anywhere**.
> **Expected:** `event.metadata` entries should be merged into the data grid, exactly as `CompactionEventView` does.

## What I actually observed

## Analysis

**Does BranchEvent have a `metadata` field?** Yes. Python: `BranchEvent(BaseEvent)` inherits `metadata: dict[str, Any] | None` from `src/inspect_ai/event/_base.py:29`. TypeScript: `generated.ts:488-491` declares `metadata?: { [key: string]: unknown } | null`. The field is real and the repro populates it legitimately (Pydantic accepts it, serialiser writes it, viewer API serves it).

**Does the source match the claim?** Yes. `BranchEventView.tsx:23-29` builds `data` from exactly two keys and passes it straight to `<MetaDataGrid>`. `event.metadata` is never read.

**Why MINOR rather than CONFIRMED:**

1. `BaseEvent.metadata` is a generic field on **every** event type. A grep of `transcript/*.tsx` shows `CompactionEventView` is the **only** event view in the entire renderer set that merges it — Model, Tool, Score, Error, Logger, Info, State, Store, Sandbox, Approval, SampleInit, ScoreEdit, Subtask, Span views all ignore it. BranchEventView follows the codebase norm; Compaction is the outlier.
2. Branch events are hidden by the default event filter (`kDefaultExcludeEvents`); users only see them under Debug.
3. The repro had to call the private `transcript()._event(BranchEvent(..., metadata=...))` to populate the field — no public API (`conversation.branch()` etc.) currently passes metadata through to a BranchEvent.

So: the observation is factually correct and the inconsistency with CompactionEventView is real, but framing it as "BranchEventView discards metadata" overstates it — almost no event view renders this field, and there's no production code path that sets it on a BranchEvent.

## Recommended action

Downgrade severity to **INFO**. If acted on at all, the fix should be codebase-wide ("event views should surface `BaseEvent.metadata` when non-null") rather than Branch-specific. Alternatively, close as BY_DESIGN given CompactionEventView is the special case, not BranchEventView.
