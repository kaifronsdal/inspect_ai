# F11.1 — Tool errors render identically to successful output

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 11-tools | **Port:** 7627 | **Log:** `2026-04-23T04-58-06-00-00_F11.1-tool-error-styled-as-success_eg5pi9xwMDxw7zEsMWuFpk.eval`

## What the finding claims

`ToolEventView.tsx:110` and `ChatMessageRow.tsx:228-231` flatten `ToolCallError` to `.message` and pass it through the same `output` prop as a successful result, so a failed tool call gets no error styling, icon, or label — visually indistinguishable from a tool that succeeded and printed text.

## What the repro's bug_description says to look for

> **Observed:** The ❌ error result is rendered as a plain grey `<pre>` block, byte-for-byte identical styling to the ✅ success result. No error icon, colour, or label.
> **Expected:** The error result has distinct styling — e.g. red left-border + `Error (unknown):` prefix — like `ServerToolCall.tsx` already does for server tools.

## Analysis

The screenshot read and DOM diff agree exactly with the finding and the prior verdict. The two tool-event cards are byte-for-byte identical in CSS classes and inline styles; the failing panel carries **zero** classes the succeeding panel lacks, and no error icon/badge is added. Source confirms the cause: `ToolEventView.tsx:110` does `output={event.error?.message || event.result || ""}` — the error is collapsed to a string and routed through the success path; `ToolCallView` has no `error` prop. `resolveToolMessage` in `ChatMessageRow.tsx:228-231` does the same for the Messages tab. `EventPanel.tsx` has no `failed`/`error` prop, so the panel chrome can't differentiate either.

This is not BY_DESIGN: `ServerToolCall.tsx:126-129` *does* render `content.error` in distinct red/bold styling, so the codebase already treats server-tool errors differently — the regular-tool path simply never got the equivalent. Impact is real (a user scanning a long agent trace cannot spot failed calls without reading every body), so HIGH stands — not a MINOR cosmetic.

The "Error" string that appears only in the bad panel's `inner_text` is a false signal — it comes from the repro's own error message body ("…'Error:' label…"), not from any viewer-rendered label.

## Recommended action

Keep as-is (CONFIRMED, HIGH). Fix per the finding's suggestion: thread `error?: ToolCallError` into `ToolCallView` and render with distinct styling (red left-border + `Error (<type>):` prefix), matching `ServerToolCall.tsx`.
