# F11.7 — `ToolEvent.truncated` never surfaced in UI

**Prior verdict:** CONFIRMED (with note "impact overstated — Python preamble is shown; suggest → LOW")
**New verdict:** CONFIRMED_MINOR
**Batch:** 11-tools | **Port:** 7631 | **Log:** `2026-04-23T04-58-13-00-00_F11.7-toolevent-truncated-not-shown_L82QVrM7oAapAgSYfTAVHB.eval`

## What the finding claims

`ToolEventView.tsx` never reads `ToolEvent.truncated?: [number, number]`, so "users see a result that ends mid-stream with **no indication it was truncated by Inspect** rather than by the tool itself" (`findings/11-tool-call-rendering.md:169-182`). Suggested fix: a muted footer "Output truncated (showing N of M bytes)".

## What the repro's bug_description says to look for

> **Observed:** Output is shown clipped (you will NOT see `F11.7_FULL_OUTPUT_END`) but there is no UI footer saying *how much* was clipped. The `truncated` field (≈ `[2050, 200]`) is in the raw event but invisible.
> **Expected:** A muted footer like `Output truncated (showing 200 of 2050 bytes)` below the tool output.

## What I actually observed

**Screenshot:** `artifacts/per-finding/F11.7-panel.png` (also `F11.7-page.png`)

The Tool event panel for `big_output` renders a single output block. The **first two lines of that output** are a prominent, plain-English truncation banner: *"The output of your call to big_output was too long to be displayed. Here is a truncated version:"*, followed by `<START_TOOL_OUTPUT>` / `<END_TOOL_OUTPUT>` wrapping the head+tail snippet. There is **no separate viewer-chrome footer**, no byte counts, no badge — but the truncation is unmistakable to anyone reading the panel.

**DOM evidence:**
```
TOOL: BIG_OUTPUT (0 SEC)
turn 1/2
big_output
The output of your call to big_output was too long to be displayed.
Here is a truncated version:
<START_TOOL_OUTPUT>
F11.7_FULL_OUTPUT_START >>> 0123456789…0123456789 <<< F11.7_FULL_OUTPUT_END
<END_TOOL_OUTPUT>
```

Raw event (from the .eval): `truncated: (2054, 200)` — the field is present and unread.

## Analysis

**Source-code claim is correct.** `src/inspect_ai/_view/ts-mono/packages/inspect-components/src/transcript/ToolEventView.tsx` (lines 44–138) reads `event.function`, `event.arguments`, `event.view`, `event.error`, `event.result`, `event.pending`, `event.timestamp`, `event.working_time`, `event.working_start`, `event.events` — but never `event.truncated`. `rg "truncated"` over the whole `inspect-components/src/` tree confirms the field is never consumed by any view.

**Impact claim is wrong.** The finding asserts users get "no indication it was truncated by Inspect." That is false: `truncate_tool_output()` in `src/inspect_ai/model/_call_tools.py:822-846` rewrites `event.result` itself to lead with *"The output of your call to {tool} was too long to be displayed. Here is a truncated version:"*. The viewer renders `event.result` verbatim, so the truncation indicator is the very first thing the user reads in the output box. There is no "ends mid-stream with no indication" — the indication is front-and-centre.

**Repro's `observed` is also wrong** on a detail: it says "you will NOT see `F11.7_FULL_OUTPUT_END`", but Inspect uses head+tail truncation (`truncate_string_to_bytes`) so both START and END markers survive. This does not affect the verdict but the bug_description is misleading.

**Is a separate UI indicator needed?** No, not for the stated reason. The only information `event.truncated` carries that the preamble doesn't is the byte counts (2054 → 200). Surfacing those would be a minor UX nicety — "showing 200 of 2,054 bytes" is more precise than "too long to be displayed" — but it is an enhancement, not a bug. A reasonable user is not confused or misled by the current rendering.

The prior batch verdict already flagged this ("impact overstated; suggest → LOW"); this rigorous pass agrees and tightens it to CONFIRMED_MINOR.

## Recommended action

Downgrade severity **MEDIUM → LOW** and rewrite the finding's impact paragraph: change "no indication it was truncated" to "no indication of *how many bytes* were truncated (the Python preamble already tells users it was truncated; only the `(raw, kept)` byte counts are lost)". Also fix the repro `bug_description.observed` — both sentinel markers are present after head+tail truncation.
