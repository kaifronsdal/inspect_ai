# F10.2 — Standalone tool messages never show `error` and drop most content types

**Prior verdict:** NOT_REPRODUCED (the `collapseToolMessages:false` path is scout-only)
**New verdict:** REPRO_BROKEN (source-level bug confirmed; unreachable in inspect viewer)
**Batch:** 10-chat | **Port:** 7623 | **Log:** `2026-04-23T04-57-48-00-00_F10.2-standalone-tool-drops-error-content_UPW4fXJ3mphHU59LyhthL6.eval`

## What the finding claims

`ChatMessage.tsx:116-129` — when a tool message renders **standalone** (i.e. `collapseToolMessages: false`), the `isNonTaskTool` branch passes `message.content` to `<ToolOutput>` after filtering to `text|image` only and **never reads `message.error`**, so a failed tool call shows only its (often empty) content with no error indication. Contrasted with the collapsed path (`ChatMessageRow.tsx:228-231`) which *does* substitute `error.message`.

## What the repro's bug_description says to look for

> **Where:** Messages tab. If the viewer exposes a `collapseToolMessages` toggle, turn it **OFF** so the tool message renders standalone via `ChatMessage`.
> **Observed:** Only the text part renders. The `ContentAudio` and `ContentData` blocks are gone (F11.8), and the `ToolCallError(type=timeout, message="F10.2_ERROR_FIELD_timeout — ex…")` is nowhere to be seen — the failed call looks like a successful one.
> **Expected:** Audio player, ContentData record-tree, AND a distinctly-styled error block all render. Same as the collapsed path (which *does* substitute `error.message`).

## Analysis

**The tool error IS visible in the inspect Messages tab** — confirming the prior NOT_REPRODUCED observation. But the reason it's visible is that the repro never reaches the cited buggy code:

1. The inspect Messages tab is `SampleDisplay.tsx:542-562` → `<ChatViewVirtualList … tools={{ callStyle: "complete" }} />`. No `collapseToolMessages` key, so `ChatViewVirtualList.tsx:131` defaults it to `true`.
2. With `collapseToolMessages: true`, `resolveMessages()` attaches the tool message to the preceding assistant's `toolMessages[]`, and `ChatMessageRow` renders it via `resolveToolMessage()` → `ToolCallView`. That path reads `toolMessage.error?.message` (line 228-231) and shows it.
3. The cited buggy branch `ChatMessage.tsx:116-129` is reached only when a `ResolvedMessage` has `message.role === "tool"` — which requires `collapseToolMessages: false` (`ChatView.tsx:38-46`). Grep confirms only `apps/scout/src/app/utils/refs.tsx:132,146,208` set it `false`. (`ModelEventView.tsx:142,192` can also set it `false` when `hasToolEvents === false`, but that's the Transcript tab's Model-Call panel and this repro has no `ModelEvent`.)
4. The inspect viewer exposes **no UI toggle** for `collapseToolMessages`, so the repro's instruction "turn it OFF" is impossible to follow.

**Source-level validity:** I re-read `ChatMessage.tsx:116-129` and the bug is real as written — `message.error` is never referenced on that branch and content is filtered to `text|image`. The finding is **correct at source level** but **not observable in the inspect viewer**; it is `apps/scout`-scoped.

Per this protocol's taxonomy that is `REPRO_BROKEN` ("the .eval doesn't reach the code path … the underlying finding may still be valid"), which is consistent with — and refines — the prior `NOT_REPRODUCED`.

## Recommended action

Keep the finding but **re-scope to `apps/scout`** and downgrade from HIGH to MEDIUM (scout is a secondary consumer; inspect users never hit this). The repro `.eval` cannot demonstrate it in `inspect view`; either drop the repro or rebuild it against the scout app.
