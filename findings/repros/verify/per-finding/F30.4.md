# F30.4 — SecondaryBar hidden entirely unless `status === "success"`

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 30-loglist | **Port:** 7644 | **Log:** `2026-04-24T01-25-14-00-00_F30.4-secondary-bar-hidden-ERROR_2kvm8SZmwtYwGhceFBKUdL.eval`

## What the finding claims

`SecondaryBar.tsx:45-47` guards on `if (!evalSpec || status !== "success") { return null; }`, so for `error` / `cancelled` / `started` logs the entire secondary bar (Dataset, Scorer, Config, Duration) is suppressed even though the underlying data is present on `EvalSpec` / `EvalStats`.

## What the repro's bug_description says to look for

> **Observed:** No secondary bar at all — Dataset, Scorer, Config (`distinctive_arg=F30.4_TASK_ARG`), and Duration are all missing from the header even though the data is in the log (check the JSON tab to confirm).
> **Expected:** The secondary bar should render for errored/cancelled/started logs too. Only the score summary is genuinely success-gated; dataset name, task args and elapsed time are exactly what you want when triaging a failure.

## Analysis

Source at `apps/inspect/src/app/log-view/title-view/SecondaryBar.tsx:45-47` reads exactly as the finding quotes:

```ts
if (!evalSpec || status !== "success") {
  return null;
}
```

The screenshots and DOM extraction match the finding's prediction precisely: the errored log's `<nav>` contains only the PrimaryBar markup, while a sibling success log's `<nav>` additionally renders the `ExpandablePanel` with Dataset/Scorer/Duration `LabeledValue`s. The JSON tab confirms `task_args.distinctive_arg`, `stats.started_at`, and `stats.completed_at` are all populated on the errored log — the data exists but is hidden purely by the status guard.

Git history (`ts-mono` submodule) shows the guard arrived via bulk copy/refactor commits with no comment or commit message indicating it is intentional, so there is no BY_DESIGN signal. A reasonable user triaging a failed run would expect to see dataset name, task args, and elapsed duration in the header — those are exactly the triage-relevant fields. This is a real, user-visible UX bug at MEDIUM severity.

The prior verdict was correct.

## Recommended action

Keep as-is (MEDIUM). Suggested fix from the finding stands: drop the `status !== "success"` clause (keep the `!evalSpec` guard) and gate only the scorer cell on `evalResults`.
