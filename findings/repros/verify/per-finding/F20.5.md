`SampleScoresView.tsx:48-85` renders an **Input** label + `SampleScoresGrid` (Scorer/Answer/Score/Explanation) but never renders `sample.target`, so a reviewer "cannot tell whether the score is correct without flipping back to the Transcript or header."

The sample's `target` — the sentinel string `F20.5_TARGET_SHOULD_APPEAR_IN_SCORING_TAB` — appears **nowhere** on this tab. (Ctrl-F … it's only in the header row above the tabs and in this prompt text.)"

## Analysis

**Q: Is the target sentinel visible in the Scoring tab?** Not as a rendered `sample.target` field. The two occurrences inside `#scoring-contents` come from the repro's own input prompt and scorer explanation; the component itself contributes no Target row. Source confirms: `SampleScoresView.tsx` reads only `sample.input` / `sample.choices` and passes the sample to `SampleScoresGrid`, which has zero references to `target`.

**Q: Is it visible in the header?** Yes — `SampleSummaryView.tsx:135-150` pushes a labelled **Target** column into the persistent header row, and the screenshot shows it fully rendered.

**Q: Is duplicating it in the Scoring tab actually needed?** Mostly no. The finding's impact statement ("flipping back to … the header") is overstated: the header is not somewhere you flip *to* — it is pinned above the tabs and visible at the same time as the Scoring content. A reviewer comparing Answer ↔ Target can read both without any navigation. The only residual gap is that the header truncates values (`kMaxCellTextLength = 300` chars and `clamp: true`), so a very long / multi-line target would be clipped in the header while the Scoring tab's Input gets a full expandable panel — an asymmetry, but an edge case.

The technical claim reproduces exactly; the user-facing impact is minimal and arguably the current layout is intentional (header = summary of Input/Target/Answer/Score; tab = per-scorer detail). No code comment says so, so I stop short of BY_DESIGN.

## Recommended action
Downgrade severity LOW → TRIVIAL (or reclassify as an enhancement request: "add a Target panel to the Scoring tab for parity with Input, useful when target is long enough to be truncated in the header"). Prior CONFIRMED verdict was technically correct but did not weigh that the header already shows the target on the same screen.
