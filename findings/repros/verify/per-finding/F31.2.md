# F31.2 — Solver step params are never displayed

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 30-loglist | **Port:** 7646 | **Log:** `2026-04-24T01-25-05-00-00_F31.2-solver-params-not-shown_JFZkxzHQZLQp2BmGmXs94i.eval`

## What the finding claims

`SolversDetailView` (`src/inspect_ai/_view/ts-mono/apps/inspect/src/app/plan/SolverDetailView.tsx:24-27`) renders each plan step as `<DetailStep name={step.solver} />` and never passes `params={step.params}`, so solver parameters are invisible in the Info-tab Plan card. Scorers in the same card *do* pass `params` to `DetailStep`, making the omission asymmetric.

## What the repro's bug_description says to look for

- **observed:** "Solvers column shows only `parameterised_solver` (bare name). The params `my_param='F31.2_SHOULD_BE_VISIBLE'`, `threshold=0.777`, `retries=3` are nowhere to be seen — even though `EvalPlanStep.params` carries them."
- **expected:** "Solver params listed under the solver name, exactly like the Scorers column does (`includes` shows `ignore_case: true`)."

## Analysis

**Core claim — CONFIRMED.** The log file carries `plan.steps[0].params` with the sentinel string, but the rendered Solvers column is the bare name only. Source confirms why: `SolverDetailView.tsx:24-27` calls `<DetailStep name={step.solver} className=.../>` with no `params` prop, while `DetailStep.tsx:25` only renders the `MetaDataGrid` when `params` is supplied. This is data the user configured (`parameterised_solver(my_param=..., threshold=0.777, retries=3)`) that is silently dropped from the UI — a reasonable user inspecting "how was this run configured?" would expect to see it here.

**Asymmetry claim — confirmed in source, NOT visually demonstrated by this repro.** The repro's `bug_description` says the Scorer column will show `ignore_case: true` for contrast. It does not: `includes()` was called with no explicit args and `results.scores[0].params` is `{}`, so `DetailStep`'s `Object.keys(params).length > 0` guard suppresses the grid for the scorer too. However, the asymmetry is unambiguous in code:

- `ScorerDetailView.tsx:26-31` → `<DetailStep ... params={params} />`
- `SolverDetailView.tsx:24-27` → `<DetailStep name={step.solver} />` (no `params`)

So the prior CONFIRMED verdict stands on the primary observable (sentinel missing). The repro's *secondary* "look, scorers show theirs" claim is overstated for this specific `.eval` — that's a repro-quality nit, not a problem with the finding.

## Recommended action

Keep as-is (CONFIRMED, MEDIUM). Optionally improve the repro by using a scorer with a non-empty recorded param (e.g. `match(location="end")` or a custom `@scorer` with an explicit arg) so the Scorer column visibly renders a param grid and the asymmetry is observable in the screenshot, not just the source.
