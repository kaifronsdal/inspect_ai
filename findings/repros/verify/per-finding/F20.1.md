# F20.1 — SampleSummaryView header drops limit/error/time

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 20-samples | **Port:** 7634 | **Log:** `2026-04-23T04-57-47-00-00_F20.1-summary-header-drops-limit_hBXMUx9323SZQZtetJD3AR.eval`

## What the finding claims

`SampleSummaryView.tsx:76-83` — `resolveSample()` reads `limit`/`working_time`/`total_time`/`error` only when `isEvalSample(sample)` (i.e. `"store" in sample`). The sole caller (`SampleDisplay.tsx:466`) passes `selectedSampleSummary: SampleSummary`, which never has `store`, so those fields are always `undefined` and the detail header never shows Limit/Time/Error columns even though `SampleSummary` carries `limit?: string` and `error?: string`.

## What the repro's bug_description says to look for

> **Observed:** "The header shows Input / Target / Answer / Score but **no Limit column** and **no Time column**, even though this sample hit `message_limit=2`. Compare with the sample-list row, which *does* show a Limit column."
> **Expected:** "Header should show `Limit: message` (and total/working time)."

## Analysis

The verdict stands. Three independent lines of evidence agree:

1. **Rendered page** — header shows only ID/INPUT/TARGET; grid template has exactly 3 columns.
2. **Underlying data** — sample JSON has `limit.type="message"`, `total_time=0.394`, `working_time=0.315`. The data is present; the header drops it.
3. **Source code** — `SampleSummaryView.tsx:51-55` defines `isEvalSample = "store" in sample`; lines 76-80 gate `limit`/`working_time`/`total_time`/`error` on it; `SampleDisplay.tsx:466` passes `selectedSampleSummary` (typed `SampleSummary`, `client/api/types.ts:100-112`, which has no `store` but does have `limit?: string` and `error?: string`).

This is a real, user-visible information loss: a user opening a sample that hit a limit sees no indication of that in the summary header, and no Time column either. The `limitSize > 0` guard at line 185 (computed from summaries) means the column slot is conceptually reserved but never filled.

The only thing the prior check overstated is the list-vs-detail contrast — it's true at source level, but the single-sample repro can't demonstrate it visually. That doesn't change the verdict.

Note on `total_time`/`working_time`: these are *not* on the client `SampleSummary` interface (only `limit` and `error` are), so even with the fix the Time column would need the interface extended — exactly as the finding's suggested fix already notes.
