# F05.4 — StateEvent "Tools" preview only fires when exactly 1 tool added

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED_MINOR
**Batch:** 01-events | **Port:** 7616 | **Log:** `2026-04-24T18-08-42-00-00_F05.4-state-tools-preview-count_YQsWNDPy4iS6KKA83BkKqB.eval`

## What the finding claims

`generatePreview` (`StateEventView.tsx:119-169`) checks `matchingOps === requiredMatchCount`; the `add_tools` signature (`StateEventRenderers.tsx:64-74`) has one pattern (`/tools/(\d+)`), so a StateEvent that adds N≥2 tools yields `matchingOps=N, requiredMatchCount=1`, equality fails, and the friendly "Tools" preview is skipped in favour of the raw JSON diff.

## What the repro's bug_description says to look for

> **Observed:** Inconsistent. The 1-tool event (CONTROL) shows **Summary / Diff** sub-tab pills — preview fired. The 3-tool event (BUG) shows only the raw JSON diff with no sub-tab pills — preview skipped.
> **Expected:** Both events should render the friendly **Tools** preview as the Summary tab.

## Analysis

**The code-level claim is correct.** Source at `StateEventView.tsx:165` reads `if (matchingOps === requiredMatchCount)` and `add_tools.signature.add = [kToolPattern]` (length 1). Three `add /tools/N` ops give `3 !== 1` → no preview. The side-by-side repro demonstrates this unambiguously: identical op type, different rendering based purely on count.

**But user-facing impact is low**, for three independent reasons:

1. **Debug-only visibility.** `state` events are excluded by `kDefaultExcludeEvents`; users must explicitly switch the filter to Debug to see either panel.
2. **The "missing" preview is currently empty anyway.** The 1-tool Summary tab body renders as `''` because F05.1 (the `setPath` brace bug) corrupts `resolvedState.tools` before `renderTools` reads it. So today the 3-tool panel's raw diff is *more* informative than the 1-tool panel's blank Summary — the user loses nothing by the preview not firing.
3. **The headline impact claim is overstated.** The finding says "`use_tools()` solver typically adds multiple tools … the preview never fires." But `use_tools()` also replaces `tool_choice`, and the separate `use_tools` change-type (checked *before* `add_tools`, `StateEventRenderers.tsx:52-62`) has signature `{add:["/tools/0"], replace:["/tool_choice"]}` → `requiredMatchCount=2`. With N tool-adds + 1 tool_choice-replace, only `/tools/0` matches the literal `add` pattern, so `matchingOps = 1+1 = 2 === 2` and the preview **does** fire for the common path. `add_tools` is only reached when tools are added *without* a `tool_choice` change.

The inconsistency is real and the `===` is clearly a bug worth a one-character fix (`>=`), but it is cosmetic, gated behind a non-default filter, and masked by F05.1.

## Recommended action

**Downgrade severity MEDIUM → LOW.** Keep the finding (the fix is trivial and correct), but strike the "`use_tools()` … never fires" sentence from the impact paragraph — it's wrong for the common case. Consider folding the fix into the F05.1 PR since the preview is useless until F05.1 is fixed anyway.
