# F21.1 — Score column sorts alphabetically, not semantically (descriptor.compare unused)

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 20-samples | **Port:** 7639 | **Log:** `2026-04-23T04-58-46-00-00_F21.1-score-column-sort-alphabetical_DdnWJtaQFW9kwEr5soTWAW.eval`

## What the finding claims

`columns.tsx:288-314` defines the score column with a `valueGetter` and `cellRenderer` but **no `comparator`**, so ag-grid sorts pass/fail letters alphabetically (`C < I < N < P`) instead of using the semantic `C → P → I → N` order that `passFailScoreDescriptor.compare` (`PassFailScoreDescriptor.tsx:37,75-88`) explicitly encodes. All seven `ScoreDescriptor.compare()` implementations are dead code.

## What the repro's bug_description says to look for

> **observed:** Rows sort `C, I, N, P` — plain alphabetical. The sample IDs encode the expected semantic rank (`expect_rank_1_C`, `expect_rank_2_P`, `expect_rank_3_I`, `expect_rank_4_N`); after sorting they read 1, 3, 4, 2.
> **expected:** `passFailScoreDescriptor.compare` defines the order `C → P → I → N` (Correct → Partial → Incorrect → Refusal). Sorting ascending should give sample IDs in rank order 1, 2, 3, 4.

## What I actually observed

**Screenshot:** `artifacts/per-finding/F21.1-page.png`, `artifacts/per-finding/F21.1-panel.png`

The SCORE column header shows the ↑ ascending-sort indicator. Rows top-to-bottom render coloured badges **C (green) → I (red) → N (red) → P (orange)**. The ID column reads `expect_rank_1_C`, `expect_rank_3_I`, `expect_rank_4_N`, `expect_rank_2_P` — i.e. ranks 1, 3, 4, 2. The orange "Partial" badge sits *below* both red "Incorrect" and "Refusal" badges, breaking the visual quality gradient.

**DOM evidence:**
```

row-index 0:  id="expect_rank_1_C"  score-0="C"
row-index 1:  id="expect_rank_3_I"  score-0="I"

asc  sequence: ['C', 'I', 'N', 'P']   ← alphabetical
desc sequence: ['P', 'N', 'I', 'C']   ← reverse alphabetical
semantic asc would be: ['C', 'P', 'I', 'N']
```

## Analysis

**Reproduces exactly as described.** Source confirms the finding on every point:

- `columns.tsx:288-314` — score column def has `headerName`, `colId`, `width`, `valueGetter`, `cellRenderer`; **no `comparator` key**. ag-grid therefore applies its default string comparator to the raw `ScoreValue` returned by `valueGetter`.
- `PassFailScoreDescriptor.tsx:37` declares `const order = ["C", "P", "I", "N"]` and lines 75-88 implement `compare()` using `order.indexOf(...)` — clear authorial intent for semantic ordering.
- `rg "\.compare\("` across `apps/inspect/src/` returns **zero call sites** outside the descriptor definitions themselves. All seven `compare()` methods (boolean, passFail, numeric, categorical, object, list, other) are dead.

**Is alphabetical sort actually wrong, or acceptable?** It is wrong, not merely cosmetic:

1. The letters are *grades*, not labels: C=Correct, P=Partial, I=Incorrect, N=Refusal. Alphabetical puts Partial (a middling result, orange badge) *after* Incorrect and Refusal (worst results, red badges) — the colour gradient in the screenshot makes the wrongness visually obvious (green, red, red, orange instead of green, orange, red, red).
2. The codebase itself documents the intended order (`order = ["C","P","I","N"]`), so this is a regression against expressed intent, not a debatable design choice.
3. The same missing `comparator` means object/list scores would string-compare as `"[object Object]"` (effectively unsortable) and numeric NaN handling in `compareWithNan` is unreachable — the pass/fail case is just the most visible symptom.

That said, with only 4 distinct values the *grouping* still works (all C's together, etc.), so users aren't blocked — they're just misled about relative quality. MEDIUM is the right severity; this is not HIGH.

Prior verdict was correct.

## Recommended action

Keep as-is (CONFIRMED, MEDIUM). Fix is the one-liner the finding suggests: add `comparator:` to the score column def in `columns.tsx` that delegates to the descriptor's `compare()`.
