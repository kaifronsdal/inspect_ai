# F11.3 — Single content-object outputs are JSON-stringified instead of rendered

**Prior verdict:** CONFIRMED (HIGH)
**New verdict:** CONFIRMED_MINOR
**Batch:** 11-tools | **Port:** 7629 | **Log:** `2026-04-24T01-30-35-00-00_F11.3-bare-contentimage-stringified_fDrdJgsZWVuQPYE4Ur2mdx.eval`

## What the finding claims

`normalizeContent` (`ToolCallView.tsx:273-293`) only checks `Array.isArray(output)`; a bare `ContentImage` (which `ToolEvent.result`'s schema permits, `generated.ts:2869`) falls to the `else` branch and is `JSON.stringify`'d, rendering as the literal text `{"type":"image","image":"data:image/png;base64,iVBOR…"}` instead of an `<img>`.

## What the repro's bug_description says to look for

> **Observed:** `screenshot_bare` output renders as the literal text `{"type":"image","image":"data:image/png;base64,iVBOR…"}`. `screenshot_list` (same image, wrapped in `[...]`) renders as an actual `<img>` thumbnail.
> **Expected:** Both render as an `<img>`.

The repro's own docstring concedes: *"Python's `call_tools` always list-wraps a bare Content* before writing `ToolEvent.result` … so the natural execution path never emits this shape."*

## What I actually observed

**Screenshots:** `artifacts/per-finding/F11.3-page.png`, `F11.3-panel-bare-only.png`, `F11.3-panel-list-only.png`

- **`screenshot_bare` panel:** renders a **RecordTree** (key/value rows): `type: image` / `image:` (with a tiny `<img>` as the value) / `detail: auto`. **NOT** the raw `{"type":"image",…}` JSON text the finding describes.
- **`screenshot_list` panel:** renders a single clean `<img class="_contentImage_…">` and nothing else.

**DOM evidence:**

## Analysis

**Code path is real.** `ToolCallView.tsx:273-293` is exactly as quoted: `Array.isArray` → else → `JSON.stringify`. The bare object does hit the stringify branch — that part of the finding is correct.

**Observed-behaviour description is wrong.** The stringified JSON is then routed to `ToolTextOutput`, which detects valid JSON and re-renders it via `JsonMessageContent` → RecordTree. So the user sees `type: image / image: <thumb> / detail: auto` rows — odd, but not the wall of base64 text the finding describes. The image is even still visible (as the value of the `image:` row).

**Reachability is essentially nil.** `src/inspect_ai/model/_call_tools.py:219-236` is the *only* in-tree producer of populated `ToolEvent.result`, and it unconditionally list-wraps any bare `Content*`:
```python
if isinstance(result, ContentText | ContentImage | ContentAudio | ContentVideo | ContentDocument):
    content: ... = [result]      # ← always list-wraps
elif isinstance(result, list) and ...:
    content = result
else:
    content = str(result)
...
event = ToolEvent(..., result=content, ...)
```
The other two `ToolEvent(...)` sites (`:306` pending placeholder, `:340` cancelled — `result=tool_result_content(...)` which returns `str | list`) also never emit a bare object. The repro had to bypass `call_tools()` entirely and call `transcript()._event(ToolEvent(result=ContentImage(...)))` directly to manufacture the shape.

So: a real tool returning `ContentImage(...)` → list-wrapped → renders correctly. The bug is reachable only for (a) hand-constructed `ToolEvent`s, or (b) hypothetical external log writers that emit the schema-permitted-but-never-produced bare form.

**Why this differs from prior verdict:** Prior batch verification (and `91-high-severity-verification.md`) confirmed the code reads as described and stopped there. It did not weigh that the only producer guarantees the array form, nor that the visible output is a RecordTree (with the image still shown) rather than raw JSON text.

## Recommended action

**Downgrade severity HIGH → LOW.** Keep as a defensive-coding fix (one-line `else if (typeof output === "object" && "type" in output) return [output];` to make `normalizeContent` honour its own type signature), but this is not a user-facing HIGH: the natural tool path cannot trigger it, and even when triggered the image is still displayed inside a RecordTree. Update the finding's "Observed" prose to describe the RecordTree, not raw JSON text.
