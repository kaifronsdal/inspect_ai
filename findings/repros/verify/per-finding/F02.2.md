# F02.2 / F02.3 — `injectScorersSpan` key mismatch + only-first-scorer

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED_MINOR
**Batch:** 02-transform | **Port:** 7604 | **Log:** `2026-04-23T04-57-50-00-00_F02.2-F02.3-scorers-span-injection_4MPXvHHbymqoQVe42Bwjxg.eval`

## What the finding claims

`transcript/transform/treeify.ts:179-264`: the synthetic "scorers" wrapper is stored in `spanNodes` under `event.id == kBeginScorerId` but its children are re-parented to `kScorersSpanId`, so the lookup misses and the wrapper stays empty (F02.2). After the first scorer's `span_end`, `hasCollectedScorers=true` permanently disables collection so scorers 2…N are never wrapped (F02.3).

## Analysis

**Source code confirms both bugs.** `treeify.ts:58` does `spanNodes.set(event.id, node)`; the synthetic begin span at L190-202 has `id: kBeginScorerId` / `span_id: kScorersSpanId`; collected children get `parent_id: … || kScorersSpanId` (L210); `resolveParentForEvent` (L156-160) does `spanNodes.get(parentId)` → `spanNodes.get(kScorersSpanId)` → `undefined` → root. F02.3: L232 sets `hasCollectedScorers = true` on first flush; L244-248 guard `!hasCollectedScorers` then blocks all subsequent scorer collection. The browser output matches this trace precisely.

**However — the critical question: does this code path fire for normal logs? Answer: NO.**

- `treeify.ts:240-242` short-circuits with `return events` the moment any `type === TYPE_SCORERS` span is seen.
- Python emits `async with span(name="scorers")` (→ `type="scorers"` via `_span.py:45` default `type=type or name`) at `_eval/task/run.py:1114` and `_eval/score.py:375`, since commit `b08625419` (2025-05-23) — the **same** commit that introduced `injectScorersSpan`.
- Per-scorer `span(name=scorer_name, type="scorer")` was added in `b91f5e58c` (2025-05-02). At `b08625419~1` the only spans in `run.py` were `init` and per-`scorer`; the scorer spans had `parent_id=None` (matching the repro's hand-built shape).

So `injectScorersSpan`'s active path is reachable **only for logs written in a ~3-week window (2025-05-02 → 2025-05-23)**. Every modern log short-circuits at L240. The repro had to deliberately raise `RuntimeError` inside the solver to suppress the modern `scorers` wrapper — it cannot be triggered by normal current-day evaluation.

**Impact reassessment:** Even for the affected legacy logs, the rendered tree is *faithful to the recorded data* (scorer spans had `parent_id=None`, they show at root). Nothing is hidden or mis-nested relative to what's on disk; the only loss is that the *intended cosmetic enhancement* (a synthetic "Scorers" group header) silently fails to appear. A user viewing such a log sees exactly what they'd see if `injectScorersSpan` didn't exist.

The prior CONFIRMED verdict was correct on the mechanics but did not weigh that the path is dead for ~11 months of logs and the failure mode is "enhancement no-op" rather than "wrong display".

## Recommended action

**Downgrade severity MEDIUM → LOW** (both F02.2 and F02.3). The function is genuinely broken but is effectively dead code for all logs since 2025-05-23. Fix is still trivial and worth doing (set `id: kScorersSpanId` on the synthetic begin event; collect all consecutive `type==="scorer"` spans before flushing once), but this is hygiene, not a user-facing bug.
