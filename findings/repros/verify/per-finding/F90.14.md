# F90.14 — Numeric score 1.0 rendered as `1.0` / `1` / `1.000` on three surfaces

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 90-cross | **Port:** 7658 | **Log:** `2026-04-23T04-58-40-00-00_F90.14-numeric-score-precision-A_QKm9DSyCG352poiAptrVjJ.eval` (+ `..._B`)

## What the finding claims

The same numeric score/metric value `1.0` is formatted by three different functions on three adjacent viewer surfaces: `formatPrettyDecimal` → `"1.0"` (`ResultsPanel.tsx:225`, `log-list/grid/columns/hooks.tsx:177`), `formatDecimalNoTrailingZeroes` → `"1"` (`NumericScoreDescriptor.tsx:31`), and `value.toFixed(3)` → `"1.000"` (`samples-panel/samples-grid/hooks.tsx:208`).

## What the repro's bug_description says to look for

> **Observed (bug):** `1.0` vs `1` vs `1.000` for the identical underlying value.
> **Expected:** One numeric formatter shared across headline metrics, sample list, and multi-log grid.

## Analysis

Reproduces exactly as described. Source code at the cited lines confirms each path:

- `packages/util/src/format.ts:64-79` — `formatPrettyDecimal(1)`: `(1).toString()` has no `.` → `numDecimalPlaces === 0` → `num.toFixed(1)` → `"1.0"`.
- `packages/util/src/format.ts:84-98` — `formatDecimalNoTrailingZeroes(1)`: no `.` → `num.toFixed(0)` → `"1"`.
- `apps/inspect/src/app/samples-panel/samples-grid/hooks.tsx:208` — `typeof value === "number"` → `value.toFixed(3)` → `"1.000"`.

The `F90.14-page.png` screenshot is the most damning: the headline `1.0` and the per-sample `1` are visible *on the same screen* roughly 400px apart, so a user comparing aggregate-vs-per-sample sees two different strings for what is mathematically the same number. The third format (`1.000`) appears one click away on the multi-log grid. None of these surfaces are obscure — log list, single-log sample list, and multi-log sample grid are the three primary navigation views.

Prior verdict was CONFIRMED via `checks/F90_14.py`; this rigorous re-check agrees. (Note: that check's surface-3 selector `'.ag-cell[col-id^="score_"]'` can match an empty neighbouring scorer column first — it still passes because surfaces 1+2 already differ, but the col-id dump here pins `score_returns_one_point_zero=1.000` directly.)

This is cosmetic, not a correctness bug — all three strings parse to the same number. LOW severity is appropriate; not downgrading further because the inconsistency is on primary surfaces and the finding's stated user-confusion rationale ("looks like they computed different things") holds.

## Recommended action

Keep as-is (LOW). Fix by routing all three through one formatter — `formatPrettyDecimal` is the obvious candidate since two of four call sites already use it.
