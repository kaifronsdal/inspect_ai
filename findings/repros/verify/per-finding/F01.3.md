# F01.3 — ScoreEditEventView renders the `"UNCHANGED"` sentinel as real data

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 01-events | **Port:** 7602 | **Log:** `2026-04-24T01-27-34-00-00_F01.3-score-edit-unchanged-sentinel_SdtNoQ7s6NoYpa6GCVtjZD.eval`

## What the finding claims

`ScoreEditEventView.tsx:50-74` checks `kUnchangedSentinel` only for `answer` (L63) and `metadata` (L118). For `value` it does `event.edit.value ? <ScoreValue score={event.edit.value}/>` — the string `"UNCHANGED"` is truthy so it renders as a real score; `explanation` is passed straight to `<RenderedText markdown={...}/>` with no sentinel guard.

## What the repro's bug_description says to look for

> **Observed:** The *Value* row shows the string `UNCHANGED` styled like a real score, and the *Explanation* row shows the literal text `UNCHANGED`.
> **Expected:** Value and Explanation rows should be hidden (or show '—'), since this edit only modified `answer`. Only the Answer row should show a new value (`edited-answer-only`).

## What I actually observed

**Screenshot:** `artifacts/per-finding/F01.3-panel.png` (also `F01.3-page.png`)

The Edit Score panel renders an "UPDATED VALUES" grid with three rows. **VALUE** shows the bold text `UNCHANGED` (ScoreValue styling — indistinguishable from a real string score). **ANSWER** shows `edited-answer-only` (the one field the repro actually edited). **EXPLANATION** shows the plain text `UNCHANGED`. There is no `[unchanged]` placeholder or visual indication that VALUE/EXPLANATION are sentinels rather than user-supplied data.

## Analysis

Exact match between claim, source, and rendered output:

- **Source confirms:** L50 `event.edit.value ? ...` (truthy check, no `=== kUnchangedSentinel`); L73 `markdown={event.edit.explanation || ""}` (no sentinel check). Contrast L63-67 where `answer === kUnchangedSentinel` renders `<pre className={styles.unchanged}>[unchanged]</pre>` — proving the sentinel was *meant* to be special-cased and the omission for value/explanation is a bug, not design.
- **Schema confirms:** `generated.ts:2380-2406` defaults all four fields to the literal `"UNCHANGED"`.
- **Screenshot confirms:** VALUE renders `UNCHANGED` in bold score styling; EXPLANATION renders `UNCHANGED` as a markdown paragraph. A user reading this panel would reasonably conclude the editor set the score's value to the string `"UNCHANGED"` and its explanation to `"UNCHANGED"` — both false.
- **Not a description-bleed false positive:** the provenance reason also contains the word "UNCHANGED", but the assertion anchors on the line *immediately following* the VALUE / EXPLANATION labels, and the outerHTML shows the sentinel inside the ScoreValue / markdown-content slots, not the provenance block.

A reasonable user would consider this a bug: the panel header says "Updated Values" yet two of the three rows display internal sentinel strings as if they were edits. Any real-world `ScoreEdit` that touches fewer than all four fields (the common case) hits this.

## Recommended action

Keep as-is (HIGH). Fix is one-line per field: guard `value` and `explanation` with `!== kUnchangedSentinel` exactly as `answer` already does (this also fixes F05.5's inverse falsy-value case for `value`).
