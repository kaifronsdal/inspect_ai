# F05.1 — `setPath` brace-placement bug → state diffs render at wrong path

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 01-events | **Port:** 7615 | **Log:** `2026-04-24T01-27-48-00-00_F05.1-state-setpath-wrong-diff_ML3kiiAcBKW7reTrTeyANb.eval`

## What the finding claims

`StateEventView.tsx:292-308`: in `setPath`, the `current = current[key]` advance is *inside* the `if (key && !(key in current))` block. When an intermediate key already exists (always true after `initializeArrays()` runs), `current` never advances and the final value is written at the wrong depth — producing a phantom top-level key in the diff.

## What the repro's bug_description says to look for

> **observed:** "The diff shows the BEFORE → AFTER change under a **phantom top-level `LOOK_HERE` key** (sibling of `metadata`), and `metadata.LOOK_HERE` is shown as an empty object `{}` on both sides."
> **expected:** "The change should appear at `metadata → LOOK_HERE → nested_key` (the actual JSON-Pointer path `/metadata/LOOK_HERE/nested_key`). There should be NO top-level `LOOK_HERE` key."

## Analysis

**Verdict: CONFIRMED.** The diff tree is wrong exactly as the finding predicts.

- **Source code matches the claim.** At `StateEventView.tsx:300`, `current = current[key] as Record<string, unknown>;` sits inside the `if (key && !(key in current)) { … }` block opened at line 294. The fix (move it outside the `if`) is plainly correct.
- **Mechanism traces cleanly.** For path `/metadata/LOOK_HERE/nested_key`: `initializeArrays()` first creates `target.metadata = {LOOK_HERE: {}}`. Then `setPath` at i=0 sees `'metadata' in target` → skips body → `current` stays at root. At i=1, `'LOOK_HERE' in target` is false → creates `target.LOOK_HERE = {}` and advances. Final write lands at `target.LOOK_HERE.nested_key`. Both `before` and `after` end up `{metadata:{LOOK_HERE:{}}, LOOK_HERE:{nested_key:…}}`; jsondiffpatch diffs them and shows only the differing top-level `LOOK_HERE`.
- **Minor inaccuracy in repro `observed` text:** it says "`metadata.LOOK_HERE` is shown as an empty object `{}` on both sides" — in fact `metadata` does not appear at all, because jsondiffpatch elides keys that are identical on both sides. The core claim (phantom top-level `LOOK_HERE`, no `metadata` parent) is exactly what renders. This wording nit does not affect the verdict.
- **User impact is real.** A user reading this diff would conclude the solver mutated a top-level `LOOK_HERE` field on `TaskState`; the actual mutation was three levels deep at `state.metadata["LOOK_HERE"]["nested_key"]`. This generalises to every multi-segment StateEvent path (`/messages/N/...`, `/output/choices/N/...`), so it corrupts essentially all non-trivial state diffs. HIGH severity is warranted.
- **Agrees with prior verdict.** The previous CONFIRMED + re-audit both stand.

## Recommended action

Keep as-is (CONFIRMED, HIGH). Optionally tighten the repro's `observed` wording to "…and `metadata` does not appear in the diff at all (it is identical-empty on both sides so jsondiffpatch elides it)".
