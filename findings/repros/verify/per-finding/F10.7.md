# F10.7 — System-message collapsing loses ids, metadata, position

**Prior verdict:** CONFIRMED (re-audited 2026-04-24: "merging is intentional; the listed side-effects are observed")
**New verdict:** CONFIRMED
**Batch:** 10-chat | **Port:** 7626 | **Log:** `2026-04-23T04-57-53-00-00_F10.7-system-messages-merged-hoisted_GiLqwES45NgkExcr7PzM9o.eval`

## What the finding claims

`packages/inspect-components/src/chat/messages.ts:62-105` merges all system messages into one synthetic message with hard-coded `id: "sys-message-6815A84B062A"` and `metadata: null`, then `unshift`s it to position 0. Consequences: per-system-message metadata is dropped (other roles' metadata *is* rendered via `ChatMessage.tsx:132-142`), original ids are lost, and mid-conversation system injections are hoisted to the top — misrepresenting conversation order.

## What the repro's bug_description says to look for

> **Observed:** All three system messages are concatenated into a single synthetic system row at the very top of the conversation. Mid-stream system injections (#2 between turns, #3 at the end) are misplaced. Per-message `metadata` is lost (synthetic row has `metadata: null`).
> **Expected:** Each system message renders at its actual position in the message list, with its own id and metadata preserved.

## Analysis

**Is the merge+hoist intentional?** Yes. `messages.ts:62-105` is explicit: comment `// Collapse system messages`, builds a synthetic `ChatMessageSystem` with `metadata: null` (line 98), and `collapsedMessages.unshift(...)` (line 103). `git log -S "Collapse system messages"` traces this to `3f5bf2b3a initial commit`. The *mechanism* is unquestionably by-design.

**Is the metadata loss a bug?** Yes — and it is what the finding actually claims. The finding's title is "System-message collapsing **loses** ids, metadata, timestamps"; it documents the *consequences* of an intentional collapse, not the collapse itself. Those consequences are real and verified:

1. **Metadata is dropped** — the synthetic row hard-codes `metadata: null`, so `ChatMessage.tsx:132` (`message.metadata && Object.keys(...).length > 0`) renders nothing. The three `{"sentinel": "F10.7_SYSTEM_N_METADATA"}` dicts are in the log (JSON tab proves it) but invisible in the Messages tab. Every other role's metadata *is* rendered by the same component — system is uniquely lossy.
2. **Mid-stream order is misrepresented** — system message #2 (originally between assistant-A and user-B) and #3 (originally last) are both hoisted above assistant-A. A user debugging an agent loop that injects reminder system prompts mid-conversation cannot tell *when* the model saw each injection.
3. **Original ids are lost** — the synthetic id `sys-message-6815A84B062A` replaces the three real ids, so `messageLabels[originalId]` and copy-link-to-message can never address an individual system message.

"By design" applies to the collapse; it does **not** make the data loss correct. The collapse could trivially preserve metadata (e.g. merge the dicts, or render each source message's metadata block under the merged row). Setting `metadata: null` discards user-authored data that the viewer otherwise promises to show.

**Verdict:** CONFIRMED. Agrees with the prior verdict and the re-audit. This is not BY_DESIGN because the finding targets the side-effects, all of which are (a) observed, (b) inconsistent with how every other role is handled, and (c) something a reasonable user would consider a bug when inspecting agent traces.

## Recommended action

Keep as-is (CONFIRMED, MEDIUM). Tighten the finding's lede to read *"The viewer intentionally collapses all system messages into one top-of-list row (`messages.ts:62-105`, since initial commit); this collapse discards per-message metadata/ids and hoists mid-stream injections out of order:"* — so reviewers don't dismiss it as "they meant to do that". A fix should either (a) stop collapsing when system messages are non-contiguous, or (b) merge/preserve metadata on the synthetic row.
