# F80.10 — formatPrettyDecimal / formatDecimalNoTrailingZeroes break on scientific notation

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED_MINOR
**Batch:** 90-cross | **Port:** 7651 | **Log:** `2026-04-23T04-58-45-00-00_F80.10-tiny-score-shows-zero_XqpZYrvberX6qWpQZwZQC7.eval`

## What the finding claims

`packages/util/src/format.ts:64-98` — both formatters use `num.toString().split(".")` to count decimal places; for `|n| < 1e-6` JS returns exponential notation (`"1.234e-7"`), so the "decimal part" is `"234e-7"` (len 6) and the value collapses to `"0.000"` / `"0.000000"`. Used by the title-bar headline metric (`formatPrettyDecimal`) and per-sample Score column (`formatDecimalNoTrailingZeroes` via `NumericScoreDescriptor.tsx:31`).

## What the repro's bug_description says to look for

> **Observed:** Headline metric / log-list show **`0.000`**. Sample-list Score column shows **`0.000000`**. Both indistinguishable from a true zero score, even though the actual value is `1.234e-7`.
> **Expected:** Render in exponential form (`1.234e-7`) or enough significant figures to distinguish from zero.

## Analysis

**Reproduces exactly as described.** Source at `format.ts:68-69` / `:91-94` does the `toString().split(".")` dance the finding describes; the DOM and screenshots match the predicted outputs.

**However, the two halves of the claim have very different weight:**

1. **`formatPrettyDecimal` → `"0.000"` is *not* caused by the toString() bug.** With `maxDecimals=3`, *any* value `< 0.0005` renders as `"0.000"` via plain `toFixed(3)` — see `0.0001234` and `1e-6` above, which take the non-exponential code path and *still* give `"0.000"`. Correctly counting 10 decimal places for `1.234e-7` would yield the identical output. So the headline-metric / log-list `"0.000"` is ordinary 3-dp rounding, not evidence of the parsing bug. (The `1e-7 → "0.0"` edge *is* the bug — no `"."` → `toFixed(1)` — but that's not what the repro exercises.)

2. **`formatDecimalNoTrailingZeroes` → `"0.000000"` *is* a genuine bug.** This function's contract is "show the number, drop trailing zeros" — i.e. preserve significant digits. It correctly renders `0.0001234` as `"0.0001234"` (7 chars of precision), but at the arbitrary `1e-6` boundary (where JS switches to exponential `toString()`) it discontinuously collapses `1.234e-7` to `"0.000000"` — *adding* trailing zeros and dropping every significant digit. That is contrary to the function's name and intent, and is what the sample-list Score column shows.

**Is `"0.000"` actually a problem given tiny scores ≈ zero?** For the headline metric at 3 dp: no — that's reasonable rounding and a user would accept it. For the per-sample score: yes, it's a problem in principle. The per-sample formatter is *designed* to show full precision (it happily prints `0.0001234`), so silently flooring to zero only when `|n| < 1e-6` is a correctness defect, not a display-precision choice. Real use cases exist (per-sample log-loss, KL, p-values, ASR over large corpora) where `1e-7` vs `0` matters. **But** scores in this regime are uncommon in Inspect's typical accuracy/match workloads, and the user can still see the raw value in the JSON/Scoring tabs.

The prior CONFIRMED verdict was correct on the facts but overstated the headline-metric half (which is just rounding) and didn't weigh rarity.

## Recommended action

**Downgrade severity MEDIUM → LOW.** Keep the finding but reframe it around `formatDecimalNoTrailingZeroes` (the real defect: discontinuity at `1e-6`, output contradicts function name). The `formatPrettyDecimal` "0.000" example should be dropped or replaced with the `1e-7 → "0.0"` / `1e21` cases, which actually demonstrate the parsing bug changing output. Fix is trivial: guard with `if (!Number.isFinite(num) || Math.abs(num) < 1e-6 || Math.abs(num) >= 1e21) return num.toExponential(...)` or use `Intl.NumberFormat`.
