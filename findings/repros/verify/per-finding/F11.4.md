# F11.4 — `ToolCallContent.format="text"` ignored, content rendered as markdown

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 11-tools | **Port:** 7630 | **Log:** `2026-04-23T04-58-12-00-00_F11.4-toolcallcontent-format-text-ignored_n9DvWmUEJknUfkMw5w6zJW.eval`

## What the finding claims

`ToolInput.tsx:36-43` unconditionally passes `toolCallView.content` to `<RenderedText markdown=…>`, never branching on `toolCallView.format`. Python's `ToolCallContent.format: Literal["text","markdown"]` (`tool/_tool_call.py:18`) is therefore silently ignored — `format="text"` content containing `#`, `**`, `[...]()` gets markdown-parsed.

## What the repro's bug_description says to look for

> **Where:** Messages tab → the `plain_text_tool` call's INPUT block (the custom view above the output).
> **Observed:** The first line renders as a large H1 heading; the second line is bold; the fourth is a hyperlink. The `format='text'` flag was not honoured.
> **Expected:** All lines render as monospace literal text inside a `<pre>` (or equivalent), with `#`, `**`, `[...]()` shown verbatim.

## What I actually observed

**Screenshot:** `artifacts/per-finding/F11.4-page.png` (full page), `artifacts/per-finding/F11.4-panel.png` (tool-input view only)

The panel screenshot shows the tool-call custom view rendering as parsed markdown: line 1 is a bold heading (the `#` is gone), line 2 is bold (the `**` are gone), line 3 is a `•` bullet item, and `not a link` is a blue underlined hyperlink. None of the markdown sigils `# ** - [ ]( )` appear as literal characters. (Minor: the `<h1>` is styled fairly small in this context so it isn't a *giant* heading visually, but it is unmistakably a heading element and the bullet + hyperlink are obvious to any user.)

**DOM evidence** (outerHTML of `[class*="toolView"]`):

`inner_text()` contains **no** literal `# This line…` — the `#` was consumed by the markdown parser.

## Analysis

All three layers agree:

1. **Log integrity** — `read_eval_log()` confirms the persisted `ToolCall.view` has `format='text'` and `content="# This line should be PLAIN TEXT…"`. The repro is sound.
2. **Source** — `ToolInput.tsx:36-43` on current `main`:
   ```tsx
   if (useToolView) {
     return (
       <RenderedText
         markdown={toolCallView.content || ""}
         …
   ```
   No reference to `toolCallView.format` anywhere in the file. The finding's reading of the code is correct.
3. **Rendered DOM** — `<h1>`, `<strong>`, `<ul>/<li>`, and `<a href="http://example.invalid">` all present where literal text was requested.

A tool author who sets `format="text"` to display content containing markdown metacharacters (e.g. a diff, a config file, shell output) will see it mangled. This is a real correctness bug that violates the documented Python contract; impact is non-trivial (data corruption in display), so MEDIUM severity is appropriate. Prior verdict stands.

*(Note: there is no `Tool:` event in the transcript — the repro injects messages directly without executing a tool — so the Messages tab is the correct and only place to observe this. `ToolInput.tsx` is the shared renderer for both paths, so this does not weaken the finding.)*

## Recommended action

Keep as-is (CONFIRMED, MEDIUM). Fix: branch on `toolCallView.format === "text"` → render in `<pre>`/`Preformatted`; else `<RenderedText markdown=…>`.
