# F03.4 — Outline chevron click bubbles to row → onSelect fires

**Prior verdict:** CONFIRMED *(partial — selection jumps, no scroll in inspect; downgraded MEDIUM→LOW)*
**New verdict:** `CONFIRMED_MINOR`
**Batch:** 02-transform | **Port:** 7609 | **Log:** `2026-04-24T18-32-17-00-00_F03.4-outline-chevron-bubbles_mJHRyDcn3CjNWS3J9Ykwno.eval`

## What the finding claims

`OutlineRow.tsx:64-73`: the chevron toggle's `onClick` lacks `e.stopPropagation()`, so clicking it bubbles to the row's `onClick` which fires `onSelect` **and** `onNavigateToEvent`. Claimed impact: *"collapsing/expanding an outline node also scrolls the main transcript … users get yanked to a new scroll position."*

## What the repro's bug_description says to look for

> **observed:** "`SECOND` collapses **and** its row becomes bold/selected — the highlight jumps from `FIRST` to `SECOND` … The transcript scroll position does **not** change (the finding's scroll claim is wrong for `apps/inspect` — `onNavigateToEvent` is `undefined` here; only `apps/scout` wires it up)."
> **expected:** "Only the outline node collapses. `FIRST` stays selected; transcript scroll position unchanged."

## Analysis

**Source confirms the mechanism.** `OutlineRow.tsx:59-73` — row `onClick` calls `onSelect?.(node.id); onNavigateToEvent?.(node.id);` and the nested toggle `onClick` (lines 66-70) calls only `setCollapsed` with no `e.stopPropagation()`. Contrast `TimelineSwimLanes.tsx:569-575` where `handleChevronClick` *does* `e.stopPropagation()`. So the bubbling is real and the code-level inconsistency is real.

**Selection change: yes.** Clicking exactly the 9×10 px `<i>` element added `_selected_moh1w_9` to `SECOND`'s row. The bubble → `handleOutlineSelect` → `setSelectedOutlineId` path fired.

**Scroll change: no.** `scrollTop` stayed at 2100; URL `?event=` param unchanged. This matches source: `apps/inspect/TranscriptPanel.tsx` never passes `outline.onNavigateToEvent` (grep confirms — only `apps/scout/TimelineEventsView.tsx` wires it), and the chevron sits outside the `<a>` link so no router navigation occurs. **The finding's headline impact ("yanked to a new scroll position") is false for `apps/inspect`.**

**Would a user care?** Barely. In `apps/inspect` the *only* observable effect is `font-weight: 800` moving to the clicked row (`OutlineRow.module.css:9-11`). The bold highlight is a scroll-position tracker (`useScrollTrack`) that auto-updates on the next scroll anyway, so the desync self-heals immediately. Many tree UIs (Explorer, Finder) select-on-chevron by design; a user would not file this as a bug. The only genuine impact is in `apps/scout` (not under test here) where `onNavigateToEvent` *is* wired and would scroll.

**vs. prior verdict:** Agrees with the re-audit's measurements. I'm tightening CONFIRMED→CONFIRMED_MINOR because, asked directly whether the inspect-observable symptom is "a bug a user would care about," the honest answer is *no* — it's a cosmetic font-weight change that self-corrects on scroll.

## Recommended action

**Downgrade severity to LOW** (already done) and reframe the finding as "missing `stopPropagation` — inconsistent with swimlane chevron; causes scroll-jump in `apps/scout` only." Keep the fix (one-liner `e.stopPropagation()` at `OutlineRow.tsx:66`) since it's trivial and restores consistency, but the inspect-app symptom alone would not justify a MEDIUM.
