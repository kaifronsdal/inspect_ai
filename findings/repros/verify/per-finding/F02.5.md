# F02.5 — `reduceDepth` recursion hard-codes `1`, breaking handoff unwrap

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED (recommend severity downgrade — see Analysis)
**Batch:** 02-transform | **Port:** 7606 | **Log:** `2026-04-23T04-57-54-00-00_F02.5-handoff-reducedepth-hardcoded_CZMTtq7zi8UsMAsy7kABjF.eval`

## What the finding claims

`transform.ts:216-238`: `skipThisNode` (the `unwrap_handoff` processor) calls `reduceDepth(newNode.children, 2)`, but `reduceDepth` always recurses with hard-coded `1`. Net effect for a handoff at depth D: tool→D, tool's child (agent)→D (same as parent), grandchildren→D+2 (skips D+1).

## What the repro's bug_description says to look for

> **Observed:** The agent span sits at the **same** indent level as the `transfer_to_subagent` tool call (its parent). The agent span's own children then jump **two** indent levels to the right.
> **Expected:** The agent span should be **one** indent level under the tool call, and its children one further level under that — a smooth +1/+1/+1 staircase.

## Analysis

**Source check** — `transform.ts:219` is `reduceDepth(newNode.children || [], 2)`; `transform.ts:232-234` is `if (node.children.length > 0) { node.children = reduceDepth(node.children, 1); }` — recursion ignores the `depth` parameter. The finding's reading of the code is correct.

**Primary observable confirmed** — TOOL and its child AGENT both render at `x=472.0` / `paddingLeft=0em` / depth 0. A user would read them as siblings. This is exactly what `reduceDepth(children, 2)` produces: the first level gets `−2` while it should get `−1`.

**Secondary observable NOT confirmed** — The repro's `observed` text and the finding's math both predict the agent's children land at D+2. The page shows them at D+1. The whole agent subtree is uniformly shifted left by 1, not the 0/+2 staircase the math predicts. (REAUDIT.md attributes the missing extra step to a downstream uniform −1; I could not pin down which transform — the swimlane `selectedEvents` path re-treeifies a subset of events at depth 0 and the bookkeeping diverges from the full-log trace.) Either way the *visible* defect is "agent flush with tool", which is real.

**Repro fidelity to real `handoff()` — does NOT match.** I generated a real handoff log (`react(tools=[handoff(sub())])` against mockllm) and dumped its event stream:

```
SPAN_BEGIN  type='handoff'  id=3XCf…
SPAN_BEGIN  type='tool'     id=HwGQ…  parent_id=3XCf…
TOOL_EVENT  span_id='LxnvCBkS…'       ← outer react agent span, NOT the tool span
SPAN_BEGIN  type='agent'    id=itzc…  parent_id=HwGQ…
```

The `ToolEvent` is constructed at `_call_tools.py:306` **before** the handoff/tool spans open, so `model_post_init` captures `current_span_id()` = the *caller's* span. The repro instead sets `ToolEvent(span_id=TOOL)`, making it a child of the tool span. With the **real** `span_id`:

- `treeify` parents the ToolEvent under the outer agent span, not the tool span
- `unwrap_tools` finds no `tool`-event child → returns `null` (per the comment at `transform.ts:182-186`)
- `unwrap_handoff` sees `children[0].event.event === "span_begin"` (not `"tool"`) → matcher returns `false`
- **`skipThisNode` is never invoked** on logs generated by current `handoff()`

So `reduceDepth(…, 2)` at line 219 is presently **unreachable from production `handoff()`**. The matcher's expected shape corresponds to the pre-`d0781f99a` (Sep 2025) order-based treeify; since the span_id-based treeify landed, the transformer is effectively dead code for fresh logs. The repro's docstring claim that it "Builds the exact span/event shape that the real `handoff()` flow produces" is **incorrect** for current inspect.

**Why CONFIRMED, not REPRO_BROKEN:** The repro *does* reach `skipThisNode` and the page *does* render the depth defect the finding predicts. The source bug is real and would bite any log whose `ToolEvent.span_id` lands on the tool span (legacy logs from order-based treeify era, or any future change that fixes the ToolEvent's `span_id` to point at its enclosing tool span — which is arguably the correct value).

## Recommended action

**Downgrade severity MEDIUM → LOW.** Keep the finding (the source bug is real and the fix is trivial: pass `depth` through the recursion or change line 219 to `reduceDepth(newNode.children, 1)`), but:

1. Update the finding text to note that `unwrap_handoff` does not currently fire on real `handoff()` output because `ToolEvent.span_id` is captured before the tool span opens.
2. Strike the "+2 jump" sub-claim from the repro's `observed` text — it is not visible in the rendered page (only the flush-with-parent part is).
3. Consider filing a separate note that `unwrap_handoff` is dead code on current logs.
