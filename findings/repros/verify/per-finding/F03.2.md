# F03.2 — Timeline-options checkboxes double-toggle when clicked directly

**Prior verdict:** FALSE_POSITIVE
**New verdict:** **FALSE_POSITIVE** (upheld)
**Batch:** 02-transform | **Port:** 7607 | **Log:** `2026-04-23T04-57-56-00-00_F03.2-timeline-checkbox-double-toggle_E3mAFhCkEVNbdih29H48bW.eval`

## What the finding claims

`TimelineOptionsPopover.tsx:54-114` — each option row has `onClick={toggle}` on the wrapper `<div>` *and* `onChange={(e)=>{e.stopPropagation(); toggle()}}` on the `<input>`. Because `stopPropagation()` on a `change` event does not block the native `click` from bubbling, clicking the checkbox glyph fires both handlers → toggles twice → **net no-op** ("checkbox flickers and reverts").

## What the repro's bug_description says to look for

> **Observed:** "The checkbox flickers and reverts to its original state. Clicking the *label text* works; clicking the *box* does not."
> **Expected:** "Clicking the checkbox square toggles the option exactly once, same as clicking the label."

## Analysis

The finding's **premise is correct**: instrumentation confirms a direct `<input>` click fires *both* the native `click` (which bubbles to the wrapper `<div>` and triggers React's `onClick`) *and* the native `change` (which triggers React's `onChange`). `e.stopPropagation()` on the change event is indeed useless here.

The finding's **conclusion is wrong**: the two handler invocations do **not** cancel out. `toggleMarkerKind` (`useTimelineConfig.ts:119-128`) is a `useCallback` that reads `storedKinds` from the render closure and calls `setStoredKinds(next)` with a **plain value**, not a functional updater:

```ts
const toggleMarkerKind = useCallback(
  (kind: MarkerKind) => {
    const current = storedKinds ?? kDefaultMarkerKinds;
    const next = current.includes(kind)
      ? current.filter((k) => k !== kind)
      : [...current, kind];
    setStoredKinds(next);
  },
  [storedKinds, setStoredKinds]
);
```

Both calls execute synchronously within the same React event flush, before any re-render, so both read the *same* closure-captured `storedKinds` and compute the *identical* `next`. Two `setStoredKinds(sameValue)` calls collapse to one state change → **single toggle**. The same closure-capture argument applies to the other rows (`setIncludeUtility(!config.includeUtility)`, `setForkRelative(!config.forkRelative)` — `config` is the render-time snapshot).

Tested both directions on two independent checkboxes (Compaction True→False, Errors False→True); both toggled exactly once. The "flicker and revert" behaviour does not occur.

(Note: `outerHTML` still shows `checked=""` on Compaction after the click — that is the static HTML *attribute* / `defaultChecked`, not the live `.checked` *property* that React controls. `is_checked()` and the screenshots reflect the live property.)

## Recommended action

**Remove finding** (or downgrade to INFO/code-smell). The double-dispatch is real but harmless given the non-functional setter. It would only become a real bug if `toggleMarkerKind` were refactored to use a functional updater (`setStoredKinds(prev => …)`) — worth a code comment, not a MEDIUM bug.
