# F03.3 — Swimlane row keys use `/` as separator but span names may contain `/`

**Prior verdict:** NOT_REPRODUCED
**New verdict:** FALSE_POSITIVE
**Batch:** 02-transform | **Port:** 7608 | **Log:** `2026-04-23T04-57-58-00-00_F03.3-swimlane-slash-in-span-name_VXgBHWdqD7pJ64JBjQcM6M.eval`

## What the finding claims

Row keys are built as `${parentKey}/${displayName.toLowerCase()}` (`swimlaneRows.ts:273`); `buildBreadcrumbs` (`TimelineSwimLanes.tsx:57`) splits on `/`, looks up phantom prefixes that don't exist, "and drops it" → "breadcrumbs show gaps". Also claims `visibleLayouts` ancestor-collapse (`:237-245`) and `parentKeys` (`:188-199`) mis-parse.

## What the repro's bug_description says to look for

> **observed:** "Breadcrumb trail has missing/phantom segments (e.g. it tries to show `supervisor › my_pkg › my_module › …` where `my_pkg` and `my_module` are not real ancestors). Expand/collapse may mis-associate the parent because the ancestor key `supervisor/my_pkg` does not exist in the row map."
>
> **expected:** "Breadcrumb shows exactly `supervisor › my_pkg/my_module/weird_agent`. Collapse/expand of `supervisor` correctly hides/shows the slashed child row."

## Analysis

The page renders the **correct** breadcrumb trail; the claimed observable ("breadcrumbs show gaps", "phantom segments") does not occur. Re-reading the source confirms why the finding's impact prediction is wrong:

- `buildBreadcrumbs` (`TimelineSwimLanes.tsx:57-68`) does split on `/` and does probe phantom prefixes (`supervisor/my_pkg`, `supervisor/my_pkg/my_module`), but the `if (layout)` guard at **:63** silently skips misses — so no phantom segments appear.
- Real ancestors are **never** missed: a child key is constructed as `` `${parentKey}/${name}` `` (`swimlaneRows.ts:273`), so the parent's full key is *always* an exact prefix that the loop reconstructs at some `i`. No gaps possible.
- `visibleLayouts` (`:234-246`) probes phantom ancestor keys via `isRowCollapsed`, which returns `false` at **:223** when `layouts.find` misses → phantom keys never hide a row.
- `parentKeys` (`:187-199`) uses `startsWith(layout.key + "/")`, which is satisfied by any real child regardless of slashes in the child's name.

The finding itself acknowledges the drop ("…and drops it") but then incorrectly concludes "gaps" — that leap is the misread. The only way to produce a *wrong* breadcrumb is a key **collision**: a sibling row whose own key happens to equal a phantom prefix (e.g. a sibling span literally named `my_pkg` alongside `my_pkg/my_module/weird_agent`). The repro does not construct that, and the finding does not describe it.

The prior NOT_REPRODUCED verdict was correct on the facts; promoting to FALSE_POSITIVE because the per-finding protocol has no NOT_REPRODUCED bucket and the source-code re-read confirms the finding's stated impact cannot occur as described.

(Minor cosmetic aside, not the finding's claim: the breadcrumb *divider glyph* is `/`, so in-name slashes and dividers look similar at a glance; the divider's lighter colour + spacing keeps them distinguishable in the screenshot.)

## Recommended action

**Remove finding** (or rewrite as a LOW-severity "row-key collision when sibling name equals a slash-prefix of another sibling" with a new repro that actually constructs the collision). As written, the impact claim is false.
