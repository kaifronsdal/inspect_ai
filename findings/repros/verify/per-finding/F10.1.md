# F10.1 — Orphan tool messages are silently dropped

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED (recommend severity → MEDIUM)
**Batch:** 10-chat | **Port:** 7622 | **Log:** `2026-04-23T04-57-47-00-00_F10.1-orphan-tool-message-dropped_hFLuQGaFWGPgohGnUsNJjE.eval`

## What the finding claims

`resolveMessages` (`packages/inspect-components/src/chat/messages.ts:46-54`) attaches every `role==="tool"` message to the preceding resolved entry's `toolMessages[]` regardless of that entry's role; `ChatMessageRow.tsx:96-101` only iterates `toolMessages` when the row is `role==="assistant"` *and* has `tool_calls`. So a tool message following a user/system message (or appearing first) is collected but never rendered.

## What the repro's bug_description says to look for

> **Observed:** The conversation jumps straight from the second user turn to the third user turn — the `role=tool` message between them has vanished with no placeholder or warning.
> **Expected:** The orphan tool message containing the text `⚠️ F10.1 ORPHAN TOOL MESSAGE — IF THIS L…` should be rendered as its own row.

## What I actually observed

**Screenshot:** `artifacts/per-finding/F10.1-page.png`, `artifacts/per-finding/F10.1-panel.png`

The Messages tab renders exactly three rows, all labelled **USER** and numbered 1, 2, 3. Row 2 ("Second user turn… ↓") is immediately followed by row 3 ("Third user turn… ↑") with **nothing** between them — no tool row, no placeholder, no warning. The sentinel string is absent (the only `ORPHAN TOOL MESSAGE` substring on the page is the 40-char truncated quote inside the bug-description table in row 1).

Cross-check via JSON tab: the raw `messages[]` array contains roles `[user, user, tool, user]` and the full sentinel text plus `tool_call_id: "orphan-001"` / `function: "orphaned_tool"` — so the message *is* in the log, just not rendered.

## Analysis

**Source code matches the claim.** `messages.ts:46-54` pushes `resolved` onto `resolvedMessages[last].toolMessages` with no role check (and silently no-ops if the array is empty). `ChatMessageRow.tsx:96-101` guards the `toolMessages` render on `message.role === "assistant" && message.tool_calls?.length`. The orphan is therefore attached to the second USER row and never iterated. There is no code comment indicating this is deliberate; it's an unhandled edge of the "collapse tool results under their call" design.

**Is an orphan tool message even valid? Is dropping it arguably correct?**

- *Validity:* Per provider API contracts (OpenAI/Anthropic), a `tool` message must follow an `assistant` message with a matching `tool_call_id`, so an orphan is semantically malformed and would never be produced by a normal `generate()` loop. In that sense the input is "invalid".
- *But:* `ChatMessageTool` is a first-class type in inspect's Python API; nothing prevents a solver, message-compaction routine, or imported transcript from placing one after a non-assistant turn. The viewer is the **debugging surface** for exactly such malformed/unexpected states.
- *Is silent dropping correct?* No. Even granting that the conversation is malformed, **silently hiding a message that exists in the log** — with no placeholder, no "(orphan tool result)" badge, no count mismatch — is the worst possible behaviour for a debugging tool. A user comparing the Messages tab to provider errors would have no clue the message exists unless they open the raw JSON. "Render it standalone" or "render a warning chip" would both be acceptable; "vanish" is not.

**Severity calibration.** The trigger requires a message list that no well-formed agent loop produces, so this will not affect everyday eval browsing. The impact is real but narrow (debugging malformed conversations). HIGH feels generous; **MEDIUM** is the right level — it's silent data loss in the UI, but only on already-pathological input.

Agrees with prior verdict (CONFIRMED); only adjustment is the severity recommendation.

## Recommended action

Keep finding; **downgrade severity to MEDIUM**. Suggested fix stands: in `resolveMessages`, if the preceding entry is not `assistant`, push the tool message as its own `ResolvedMessage` (or attach a visible "orphan tool result" placeholder) instead of swallowing it.
