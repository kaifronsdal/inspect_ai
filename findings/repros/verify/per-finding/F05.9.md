## Analysis

**The symptom reproduces exactly as described** — `event.cmd === undefined` slips past the `=== null` guard and the Command section renders with two empty `<pre>` elements.

**The guard is provably dead code.** Every serialization path uses `exclude_none=True`:
- `.eval` recorder → `to_json_safe()` (`_util/json.py:94`)
- `.json` recorder → `eval_log_json()` → `to_json_safe()` (`log/_file.py:754`)
- view server API → `exclude_none=True` (`_view/server.py:95,252,517`)

So Python `cmd=None` is always *omitted* from JSON, never serialized as `null`. The JS side can therefore only ever see a string or `undefined` — **never `null`**. The `=== null` check can never be true; it's the wrong check for the wrong value.

**However: can a real SandboxEvent have `cmd=undefined`?** No — not via any production path. The Python schema permits `cmd: str | None = None` (`event/_sandbox.py:19`), but the **only** call site that constructs `SandboxEvent(action="exec")` is `util/_sandbox/events.py:94-97`, which unconditionally sets `cmd=" ".join([shlex.quote(c) for c in cmd])` — always a `str` (possibly `""`, never `None`). The repro reaches the state only by calling the private `transcript()._event(SandboxEvent(action="exec"))` directly with `cmd` omitted.

**Net:** This is a legitimate code-smell (the guard is dead code and inconsistent with sibling `ReadFileView`/`WriteFileView` which correctly use `!event.file`), and the fix is trivial (`== null` or `!event.cmd`). But the user-visible symptom (empty COMMAND heading) is unreachable through normal sandbox usage. The original finding already classified it as LOW / code-smell, which is correct; CONFIRMED_MINOR reflects that the *visual* impact is synthetic-only.

The prior CONFIRMED verdict was not wrong on the evidence (heading + empty `<pre>` does appear), but did not note the unreachability via real sandbox calls.

## Recommended action

Keep finding at **LOW / code-smell**. Fix is a one-character change (`===` → `==`, or match siblings with `if (!event.cmd)`). No severity change needed — the original LOW rating already accounts for this being defensive-code hygiene rather than a user-facing bug.
