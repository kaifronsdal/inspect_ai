# F02.1 — Sandbox grouping is a no-op in span-based logs

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 02-transform | **Port:** 7603 | **Log:** `2026-04-23T04-57-48-00-00_F02.1-sandbox-grouping-noop_bYVh8Sqz2JzkUXUiNojAC2.eval`

## What the finding claims

`groupSandboxEvents` (`fixups.ts:118-163`) wraps consecutive sandbox events in a synthetic `span_begin`/`span_end` pair, but the wrapper has `parent_id: null` and the wrapped events keep their original `span_id`. `treeifyWithSpans` (`treeify.ts:152-170`) parents non-span events by `span_id` lookup, so the sandbox events land under their *original* span and the synthetic wrapper ends up empty → stripped. Net: no "Sandbox Events" group appears in span-based logs.

## What the repro's bug_description says to look for

> **Observed:** Three individual sandbox-event rows under the solver span. No collapsible **Sandbox Events** group wrapper appears.
> **Expected:** A single collapsible **Sandbox Events** group node containing all three events (the `kSandboxSignalName` synthetic span).

## What I actually observed

## Analysis

**Source confirms the mechanism is broken.** `fixups.ts:128,132` pushes `createSpanBegin(kSandboxSignalName, ts, null)` (parent_id `null`, id `"${name}-begin"`) then `result.push(...pendingSandboxEvents)` unmodified. `treeify.ts:57-59` keys span nodes by `event.id`, and `treeify.ts:164-166` parents non-span events via `spanNodes.get(event.span_id)` — which resolves to the original solver span, never the wrapper. The wrapper becomes a childless root node and disappears.

**Is grouping actually intended?** Yes, unambiguously:
- `kSandboxSignalName` is a deliberate UUID sentinel (`53787D8A-D3FC-426D-B383-9F880B70E4AA`, `fixups.ts:11`).
- Six render paths special-case it: `SpanEventView.tsx:100-101` and `StepEventView.tsx:95` map it to title `"Sandbox Events"`; `event/utils.ts:57,68` returns label `"Sandbox Events"`; `OutlineRow.tsx:166,196` gives it a sandbox icon/label; `TranscriptOutline.tsx:165` and `TranscriptViewNodes.tsx:133` apply `removeStepSpanNameVisitor(kSandboxSignalName)` to suppress it from the outline.
- The `useSpans` branch at `fixups.ts:127` was *added specifically* to make grouping work for span-based logs (the legacy `createStepEvent` path at `:130` works correctly via `treeifyWithSteps`'s stack-based parenting). The author intended span-mode parity but mis-wired the IDs.

So this is not a "design choice to render flat" — it is a regression where the span-mode implementation of an existing feature is broken, leaving ~6 special-case branches as dead code for all modern logs.

**Is the ungrouped rendering acceptable?** It's *legible* (each sandbox event still renders correctly on its own), but it defeats the purpose of the grouping feature: with a real agentic eval that does dozens of sandbox calls per tool turn, the transcript becomes N flat rows instead of one collapsible group. The default event filter hides sandbox events entirely (`kDefaultExcludeEvents` in `sampleSlice.ts`), so users only hit this in **Debug** mode — which tempers severity but doesn't make it correct.

**Agreement with prior verdict:** Yes. The prior CONFIRMED stands; the repro accurately reproduces the claim and the source code matches the finding's reading.

## Recommended action

Keep as-is (MEDIUM). The fix is exactly as the finding suggests: rewrite each pending sandbox event's `span_id` to the synthetic span's `id`, set the synthetic span's `parent_id` to the first sandbox event's original `span_id`, and give each group a unique `id` (currently every group reuses `"${kSandboxSignalName}-begin"`). Note in the writeup that visibility is gated by the Debug filter.
