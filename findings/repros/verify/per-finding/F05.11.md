# F05.11 — SampleInitEventView omits `sample.sandbox` and `sample.id`

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED_MINOR
**Batch:** 01-events | **Port:** 7620 | **Log:** `2026-04-24T01-27-44-00-00_F05.11-sample-init-omits-sandbox-id_JRa8tJsyheohRc7TsnHSw5.eval`

## What the finding claims

`SampleInitEventView.tsx:30-108` renders Files / Setup / Choices / Target / Metadata from `event.sample`, but never reads `sample.sandbox` (the per-sample `SandboxEnvironmentSpec`) or `sample.id`. These are the only structural `Sample` fields omitted (cf. `generated.ts` `Sample` schema: `choices, files, id, input, metadata, sandbox, setup, target`).

## What the repro's bug_description says to look for

> **Observed:** The panel shows Files / Setup / Target / Metadata, but **no row for `sandbox`** (which is `local` here) and **no row for `id`** (`DISTINCTIVE-SAMPLE-ID-⚠️-F05.11`).
> **Expected:** A **Sandbox** row showing `type: local` and an **ID** row showing the sample id.

## What I actually observed

**Screenshots:** `artifacts/per-finding/F05.11-page.png`, `artifacts/per-finding/F05.11-panel.png`, `artifacts/per-finding/F05.11-panel-metadata.png`

- **SAMPLE sub-tab** shows: the user message (input), then section headings **FILES** (`hello.txt`), **SETUP** (`echo 'setup script …'`), **TARGET** (`n/a`). No SANDBOX heading. No ID heading.

- The **JSON tab** confirms the data exists in the log: `sample_init.sample.sandbox = {type: "local", config: null}`, `sample_init.sample.id = "DISTINCTIVE-SAMPLE-ID-⚠️-F05.11"`.

## Analysis

**Source-code check:** `SampleInitEventView.tsx` reads `event.sample.{files, setup, choices, target, metadata}` and `event.state.messages`. It never references `.sandbox` or `.id`. The `Sample` type (generated.ts:2187-2207) does include both. So the finding's description of the code is accurate.

**Rendered check:** Matches the claim exactly — FILES/SETUP/TARGET sections present, SANDBOX/ID absent.

**But — is it a bug a reasonable user cares about?**

- **`sample.id`:** Already displayed in the sample-dialog header *and* in the summary row immediately above the transcript. Adding a third copy inside the SampleInit panel would be redundant. This half of the finding has effectively zero user impact.
- **`sample.sandbox`:** Genuinely not surfaced anywhere in the sample dialog except raw JSON. However: (a) per-sample sandbox overrides are rare (the finding itself concedes "sandbox is usually task-level, not sample-level"), and (b) the entire SampleInit panel is **hidden under the default event filter** — you must opt into Debug mode to see it at all.

So: technically reproduces as described, source supports it, but the practical impact is one rarely-used field missing from a debug-only panel, plus one field that's already on screen twice. The prior verdict didn't weigh the `id`-redundancy or the debug-only visibility.

## Recommended action

**Downgrade severity LOW → INFO**, and rescope the finding to *only* `sample.sandbox` (drop `sample.id` — it's redundant with the dialog header). If fixed, a one-line `<EventSection title="Sandbox">` guarded on `event.sample.sandbox` is sufficient; no need to add `id`.
