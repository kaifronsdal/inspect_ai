# F04.2 — Tools sub-tab hidden when exactly one tool is defined

**Prior verdict:** CONFIRMED (HIGH¹ — flagged for severity review)
**New verdict:** CONFIRMED (downgrade to MEDIUM)

## What the finding claims

`ModelEventView.tsx:198` gates the Tools sub-tab on `event.tools.length > 1`, so a model call with exactly one tool renders no Tools tab and the tool definition / `tool_choice` are not surfaced anywhere in the event UI. Suggested fix: `> 0`.

## What the repro's bug_description says to look for

> **Observed:** Only **Summary** / **All** / **Timing** tabs are present. **No 'Tools' tab** — even though `event.tools` contains exactly one tool (`the_only_tool`).
> **Expected:** A **Tools** tab listing `the_only_tool` and its `tool_choice`.

(Minor inaccuracy: the actual tabs are Summary / All / **API**, not Timing — Timing is a section inside All. The core "no Tools tab" claim is the load-bearing part.)

## Analysis

The off-by-one reproduces exactly as claimed. Addressing the "maybe intentional?" question directly:

- **No code comment** explains the `> 1` choice.
- **Git blame** (ts-mono `a8404b2` ← parent-repo `31c309e1` "Viewer: Transcript Improvements (#1738)"): the guard was introduced as `> 1` in a bulk UI-polish PR with no rationale in the commit message; it was not a later deliberate change from `> 0`.
- **Inconsistent with sibling code:** `StateEventRenderers.tsx:216` uses `tools.length > 0` for the analogous "render tools section" check, so `> 0` is the established convention in the same package.
- **The hidden info is not redundant.** The hypothesis "the tool is visible in the call anyway" only holds if the model actually *calls* the tool — and even then only the name/args are shown, not the tool's description or parameter schema. `tool_choice` (`"auto"` vs `"none"` vs forced) is also meaningful with one tool and is hidden. In this repro the tool is entirely invisible outside raw API JSON.

So this is a genuine off-by-one, not BY_DESIGN. However, the impact is informational (one hidden tab; data recoverable from the API tab), so HIGH is overstated — agreeing with `findings/91-high-severity-verification.md` which already flagged it as PARTIAL / "MEDIUM more appropriate". This is also a duplicate of F01.4 (MEDIUM).

The prior CONFIRMED verdict stands; no error in the previous check.

## Recommended action

Keep finding; **downgrade severity HIGH → MEDIUM** and mark as duplicate of F01.4. Fix is the one-character change `> 1` → `> 0`. Optionally tweak the repro's `observed` text to say "Summary / All / API" instead of "Summary / All / Timing".
