# F20.4 — Scoring tab uses fresh single-value descriptor ≠ list/header

**Prior verdict:** CONFIRMED
**New verdict:** CONFIRMED
**Batch:** 20-samples | **Port:** 7635 | **Log:** `2026-04-23T04-58-06-00-00_F20.4-scoring-tab-descriptor-diverges_CbccjENAYWNedYHMRpY6eE.eval`

## What the finding claims

`SampleScores.tsx:17-21` builds a fresh descriptor from the single score value (`getScoreDescriptorForValues([scoreData.value], ...)`), whereas the sample list (`columns.tsx:304-306`) and header reuse `evalDescriptor.score(...)` chosen from the **full** value distribution. Because the categorizer ladder in `ScoreDescriptor.tsx` is value-set-sensitive, the same score value can render differently across the three views.

## What the repro's bug_description says to look for

> Sample `should_be_C` and `should_be_I`: list & header render `C` / `I` as **plain text** (categorical descriptor — full value-set `{C, I, X}` contains a non-pass/fail value). But the **Scoring tab** renders the same `C` / `I` as a **coloured circle badge** (pass/fail descriptor — categorises from `[C]` only).
>
> Expected: All three views should pick the same descriptor and render the score identically.

## Analysis

The divergence is real, visually obvious, and matches the finding exactly. Source code confirms the mechanism:

- `ScoreDescriptor.tsx:56-68` — passFail categorizer matches when **every** value ∈ `{C, I, P, N}`. For the eval-wide set `{C, I, X}` the `X` fails this predicate → falls through to `categoricalScoreDescriptor` (`render: score => String(score)`).
- `SampleScores.tsx:17-20` — passes `[scoreData.value]` (just `["C"]` or `["I"]`), which **does** satisfy the passFail predicate → `passFailScoreDescriptor` → `<span class={styles.circle + styles.green/red}>`.

**Is the difference confusing?** Yes. The header and Scoring grid are ~300 px apart on the same screen, both labelled "SCORE", both showing the same underlying value, yet one carries a pass/fail colour judgment (green = correct, red = incorrect) and the other is neutral text. A reviewer skimming the Scoring tab would reasonably infer the eval is a pass/fail eval; the list/header say it isn't. The `should_be_X` sample makes it worse — its Scoring tab shows plain `X`, so paging through samples C → I → X gives badge → badge → text within the same column.

Prior verdict was correct; nothing was overstated.

## Recommended action

Keep as-is (CONFIRMED, MEDIUM). Fix per the finding's suggestion: have `SampleScoresGrid`/`SampleScores` use `evalDescriptor.score(evalSample, {scorer, name})?.render()` instead of building a per-value descriptor.
