# F10.6 — Description Accuracy

**Verdict:** CONFIRMED (was BY_DESIGN; user overrode — documented behaviour but undesirable, keep as finding)
**Banner visible at Default:** yes (INFO: BUG-REPRO panel, expanded, top of Transcript)
**Inaccuracies found:** 4

## Inaccuracies fixed

1. **`observed`: "Only the 'Visible answer' paragraph renders"** → **"Row #2 begins directly with *'Visible answer: …'* The `<think>` block … is absent — no Reasoning header, no '[hidden]'/'[redacted]' placeholder, nothing."** — Two paragraphs render (the answer + the ↑ marker), not one; reworded to say the message *begins* with the visible answer, which is what's actually on screen.

2. **`where_to_look`: "the assistant turn after this description"** → **"row #2 (the assistant message)"** — The Messages tab numbers rows; row #2 has no visible "ASSISTANT" label, so "row #2" is the precise pointer.

3. **Assistant inline marker: `` "a `<think>…</think>` block ABOVE this line" ``** → **`"a think-tag block ABOVE this line"`** — The literal `<think>…</think>` inside the marker paragraph was itself being eaten by `purgeInternalContainers`, rendering as empty backticks (`` a `` block ``) in row #2. Replaced with prose so the marker reads cleanly.

4. **Framing / `extra`** — Per user instruction, did **not** lead with "BY DESIGN — NOT A BUG". Instead added a **Status** paragraph noting the strip *is* documented (`design/migration/chat-migration.md`, "Internal tag stripping") and e2e-tested (`apps/scout/e2e/chat-components.spec.ts`) as agent-bridge envelope handling, followed by a **However** paragraph: silently dropping `<think>` content with no marker is questionable — a user pasting model output containing literal `<think>` tags (raw DeepSeek-R1 / QwQ text) loses content with zero indication. Also tightened the JSON cross-check to `messages[1].content`.

## Gotcha discovered

Using `` `<think>…</think>` `` (matched open+close pair) inside the description table breaks the **Messages-tab** rendering of the USER row: `purgeInternalContainers` strips it from the source text → leaves `` `` `` (double backtick) → opens a runaway code span that swallows the rest of the table. The Transcript-tab InfoEvent banner is unaffected (not a chat message, no purge). Fix: use open-tag-only `` `<think>` `` in description fields, as the original did.
